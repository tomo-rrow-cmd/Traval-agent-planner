# AI Travel Planner 数据库设计文档

关系型数据库表结构设计与说明

当前实现核对日期：2026年7月17日

> 本文档与 `app/db/models/` 和 Alembic 迁移同步。如字段说明与源码冲突，以已执行的 Alembic 迁移和 ORM Model 为准，并应在同一变更中修正文档。

## 一、概述

本文档描述了 AI Travel Planner 项目的数据库表结构。数据库采用 PostgreSQL，使用 SQLAlchemy ORM 定义模型。所有业务表均包含以下通用字段，由 UUIDMixin 和 TimestampMixin 提供：

| 字段名 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | VARCHAR(36) | PRIMARY KEY | UUID 主键 |
| created_at | DATETIME | NOT NULL | 创建时间（UTC） |
| updated_at | DATETIME | NOT NULL | 最近更新时间（UTC） |

*表1：通用字段说明*

通用字段通过混入类（Mixin）自动注入到所有业务模型中，确保主键和时间戳的一致性。

## 三、表间关系

系统各表之间的关系如下：

- **plans.user_id → users.id**：一个用户可拥有多个旅行方案。

- **conversations.user_id → users.id**：对话归属用户（匿名会话可为空）。

- **messages.conversation_id → conversations.id**：一个会话包含多条消息，删除会话时消息级联删除。

- **conversation_plan_runs.conversation_id → conversations.id**：一个会话可拥有多次方案生成记录，conversations.plan_id 指向最近一次方案运行 ID。

- **trip_states.plan_id → plans.id**：一个方案可创建一个行程执行实例，删除方案时行程级联删除。

- **trip_states.user_id → users.id**：行程归属用户。

- **checkins.trip_id → trip_states.id**：一个行程包含多条签到记录，级联删除。

- **expense_records.trip_id → trip_states.id**、**expense_records.checkin_id → checkins.id**：花费关联行程和签到。

- **adjustments.trip_id → trip_states.id**：一个行程可有多条调整记录。

- **travelogues.trip_id → trip_states.id**：一个行程生成一篇游记。

- **social_materials.trip_id → trip_states.id**：一个行程生成多份社交素材。

- **shares.user_id → users.id**：分享归属用户；shares.target_id 多态关联 plan 或 travelogue。

- 其他表（attractions、hotels、restaurants）之间暂无直接外键关联，但业务上可通过 plans 的 JSON 字段或 checkins.poi_id 间接引用。

## 四、扩展说明

- **JSON 字段**：当前 ORM 使用 SQLAlchemy `JSON`，在 PostgreSQL 中映射为 JSON；尚未统一切换为 JSONB。

- **删除策略**：模型未使用 `SoftDeleteMixin`。删除会话 API 只把 `conversations.status` 更新为 `archived`，不会物理删除消息和方案版本；若物理删除会话，ORM 关系配置会级联删除 `messages` 和 `conversation_plan_runs`。物理删除方案会级联删除 `trip_states`，进而级联删除 checkins、expenses、adjustments、travelogues、social_materials。
