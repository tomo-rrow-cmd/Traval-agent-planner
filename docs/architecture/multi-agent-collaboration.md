## 1. 架构总览

本系统采用**多智能体协作架构（Multi-Agent Collaboration Architecture）**，由 7 个功能智能体组成，按职责划分为三层：交互层、规划层和决策层。智能体之间通过标准化 JSON 消息协议通信，遵循"提取 → 并行规划 → 决策确认 → 交通整合 → 预算核算"的流水线模式执行。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              交互层 (Interaction Layer)                      │
│  ┌───────────────────────────────────────────────────────────────────────┐   │
│  │                        用户交流智能体                                  │   │
│  │   (自然语言对话 → 意图识别 → 参数提取 → 旅行信息 JSON)                 │   │
│  └───────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                              规划层 (Planning Layer)                         │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐             │
│  │  景点规划智能体  │  │  美食规划智能体  │  │  酒店规划智能体  │  并行执行    │
│  │  AttractionAgent │  │   FoodAgent     │  │   HotelAgent    │             │
│  └─────────────────┘  └─────────────────┘  └─────────────────┘             │
│         │                      │                      │                      │
│         └──────────────────────┼──────────────────────┘                      │
│                                ▼                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐   │
│  │                        方案决策智能体                                  │   │
│  │   (候选方案展示 → 用户交互 → 倾向确认 → 每日行程定稿)                  │   │
│  └───────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                              执行层 (Execution Layer)                        │
│  ┌─────────────────┐        ┌─────────────────┐                             │
│  │  交通规划智能体  │   →    │    预算智能体    │                             │
│  │  TrafficAgent   │        │   BudgetAgent   │                             │
│  └─────────────────┘        └─────────────────┘                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. 核心设计原则

| 原则 | 说明 |
|:---|:---|
| **单一职责** | 每个智能体只负责一项核心功能，避免功能耦合 |
| **并行处理** | 景点、美食、酒店三类规划无依赖关系，并行执行以缩短响应时间 |
| **分层兜底** | 数据查询遵循「RAG 向量检索 → PostgreSQL 关系库 → 第三方 API」三级兜底策略 |
| **人机协同** | 方案决策智能体在关键节点引入用户确认，确保推荐结果符合用户真实意图 |
| **数据驱动** | 智能体间通信全部基于结构化 JSON，确保信息传递的完整性与可解析性 |
| **可扩展性** | 新智能体可通过标准化接口接入，不影响现有流水线 |

## 3. 智能体定义与职责

### 3.1 用户交流智能体

| 属性 | 说明 |
|:---|:---|
| **标识** | `UserInteractionAgent` |
| **定位** | 系统入口，唯一与用户直接交互的智能体 |
| **核心职责** | 通过自然语言对话理解用户需求，提取结构化旅行参数 |
| **数据源** | DeepSeek LLM（纯对话能力，不调用外部工具） |
| **重试策略** | LLM 调用失败时 3 次指数退避重试（1.5s → 2.25s → 3.4s） |

**内部流程：**

```
用户输入 → CHAT_PROMPT 驱动对话 → 生成自然语言回复
              ↓
         EXTRACT_PROMPT 结构化提取 → 旅行信息 JSON
              ↓
         就绪检测（关键字段完整度检查）→ ready = true → 触发规划管线
```

**就绪判定条件：**
- 目的地（destination）已确认
- 出发地（origin）已确认
- 旅行天数（days）或起止日期已确认
- 总预算（total_budget）已确认
- 以上四项为必填项，其余字段（偏好、节奏、住宿标准等）为可选项

---

### 3.2 景点规划智能体

| 属性 | 说明 |
|:---|:---|
| **标识** | `AttractionAgent` |
| **定位** | 规划层 — 景点推荐与每日游览规划 |
| **核心职责** | 根据用户偏好检索景点信息，排序筛选后分配至每一天，生成含推荐理由的日行程 |
| **数据源** | Chroma 向量库（BGE Embedding）→ PostgreSQL（坐标补充） |
| **外部工具** | `search_attractions`（本地检索）、高德 API（兜底拉取） |
| **数据不足处理** | 候选 < 3 条时，自动触发 `seed_poi.py` 从第三方拉取数据入库 |

**内部流程：**

```
偏好文本 → BGE Embedding → Chroma 语义搜索（Top 25）
              ↓
         候选 < 3? → 自动触发 seed_poi.py --city <城市> → 重试搜索
              ↓
         PostgreSQL 查坐标 → 构建候选列表（含 lat/lng）
              ↓
         候选列表 + Prompt → DeepSeek → 排序 / 筛选 / 分天 / 写推荐理由
              ↓
         Pydantic Schema 校验 → 返回结构化景点规划
```

---

### 3.3 美食规划智能体

| 属性 | 说明 |
|:---|:---|
| **标识** | `FoodAgent` |
| **定位** | 规划层 — 餐厅推荐与每日餐饮规划 |
| **核心职责** | 根据菜系偏好和预算检索餐厅，为每天分配午餐和晚餐推荐 |
| **数据源** | Chroma 向量库（BGE Embedding）→ PostgreSQL |
| **外部工具** | `search_restaurants`（本地检索）、美团 SKILL（兜底拉取） |
| **数据不足处理** | 候选 < 3 条时，自动触发 `seed_poi.py` 从第三方拉取数据入库 |

**内部流程：**

```
菜系偏好 + 预算 → BGE Embedding → Chroma 语义搜索（Top 25）
              ↓
         候选 < 3? → 自动触发 seed_poi.py → 重试搜索
              ↓
         候选列表 + Prompt → DeepSeek → 每天分午餐 + 晚餐推荐
              ↓
         Pydantic Schema 校验 → 返回结构化餐饮规划
```

---

### 3.4 酒店规划智能体

| 属性 | 说明 |
|:---|:---|
| **标识** | `HotelAgent` |
| **定位** | 规划层 — 住宿推荐与酒店预订规划 |
| **核心职责** | 根据预算和位置偏好检索酒店，推荐最优住宿方案 |
| **数据源** | 美团酒旅 CLI（优先，提供真实价格与评分）→ Chroma 向量库（兜底） |
| **外部工具** | `meituan_travel`（美团 CLI，120s 超时）、`search_hotels`（本地检索） |
| **数据不足处理** | Chroma 候选 < 3 条时，自动触发 `seed_poi.py` |

**内部流程：**

```
美团 mttravel CLI（优先）→ 1-2 分钟 → 真实价格 + 评分 + 图片
              ↓ 失败 / 超时
         Chroma RAG → 酒店候选
              ↓ 候选 < 3? → 自动触发 seed_poi.py
              ↓
         DeepSeek → 推荐 2 家 + 写理由 + 标注 price_verified
              ↓
         Pydantic Schema 校验 → 返回结构化住宿规划
```

---

### 3.5 方案决策智能体

| 属性 | 说明 |
|:---|:---|
| **标识** | `DecisionAgent` |
| **定位** | 决策层 — 人机协同的行程确认中枢 |
| **核心职责** | 汇总三种规划智能体的推荐结果，以交互方式引导用户确认每日行程细节 |
| **数据源** | 上游智能体输出（景点规划 + 餐饮规划 + 住宿规划） |
| **交互方式** | 向用户展示候选方案，询问具体选择或倾向，逐日确认 |

**内部流程：**

```
接收景点规划 + 餐饮规划 + 住宿规划
              ↓
         整合为"每日候选方案"（Day 1/2/3... 各含多个景点/餐厅/酒店选项）
              ↓
         逐日向用户展示：
              ├─ "Day 1 上午有 A、B 两个景点可选，您倾向哪个？"
              ├─ "Day 1 午餐推荐 C、D 两家餐厅，您偏好哪种菜系？"
              └─ "Day 1 住宿推荐 E、F 两家酒店，您的选择是？"
              ↓
         收集用户选择 → 确定每日最终行程
              ↓
         输出"已定稿行程" → 传递给交通规划智能体
```

**决策完成标志：**
- 每一天的景点游览顺序已确认
- 每一天的午餐、晚餐餐厅已确认
- 每一天的住宿酒店已确认（或全程住宿方案已确认）

---

### 3.6 交通规划智能体

| 属性 | 说明 |
|:---|:---|
| **标识** | `TrafficAgent` |
| **定位** | 执行层 — 大交通与市内交通路线规划 |
| **核心职责** | 制定两类交通方案：①大交通（出发地→目的地→酒店→返程）；②每日市内交通（景点间/餐厅间/酒店间） |
| **数据源** | 高德 Direction API（有坐标时精确路径）+ Haversine 公式（无坐标时估算） |
| **外部工具** | `get_route`（高德路径规划）、12306 爬虫（火车票查询） |
| **输入依赖** | 必须等待方案决策智能体输出已定稿行程后才能执行 |

**内部流程：**

```
接收已定稿行程（酒店、景点、餐厅坐标 + 出发地/目的地）
              ↓
         ┌─────────────────────────────────────┐
         │  阶段 A：大交通规划                  │
         │  出发地 → 目的地（城际交通）          │
         │  目的地 → 酒店（市内接驳）            │
         │  酒店 → 返程（城际交通）              │
         └─────────────────────────────────────┘
              ↓ 调用 get_route / 12306
         ┌─────────────────────────────────────┐
         │  阶段 B：市内交通规划                │
         │  每日路线：酒店 → 景点A → 景点B      │
         │           → 餐厅 → 景点C → 酒店      │
         └─────────────────────────────────────┘
              ↓ 调用 get_route（批量坐标路径规划）
         整合大交通 + 市内交通 → 完整交通方案
              ↓
         传递给预算智能体
```

---

### 3.7 预算智能体

| 属性 | 说明 |
|:---|:---|
| **标识** | `BudgetAgent` |
| **定位** | 执行层 — 费用汇总、预算分配与超支预警 |
| **核心职责** | 汇总所有智能体的实际费用，与预算分配进行对比，输出预算执行报告 |
| **数据源** | 确定性算法（不调用 LLM，纯计算逻辑） |
| **输入依赖** | 景点规划（门票费用）+ 餐饮规划（餐费）+ 住宿规划（房费）+ 交通规划（路费） |

**预算分配比例：**

```
住宿 35% | 交通 20% | 餐饮 20% | 门票 15% | 购物预留 10%
```

**内部流程：**

```
接收所有已定稿方案的实际费用
              ↓
         总预算 × 分配比例 → 各项预算基准
              ↓
         逐项对比（预算 vs 实际花费）
              ↓
         超支检测 → 生成 warning（如有）
              ↓
         计算人均日均花费
              ↓
         输出预算执行报告
```

## 4. 数据流转与协作流程

### 4.1 阶段一：需求提取

```
用户
 │ 自然语言对话
 ▼
┌──────────────────────┐
│  用户交流智能体       │
│  UserInteractionAgent │
└──────────────────────┘
 │  旅行信息 JSON
 │  {destination, origin, days, total_budget, preferences, ...}
 ▼
触发规划管线
```

**本阶段输出：** `TravelParams` JSON 对象，作为后续所有智能体的输入。

---

### 4.2 阶段二：并行规划

三种规划智能体**并行执行**，无依赖关系：

```
                    TravelParams
                         │
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
│  景点规划智能体  │ │  美食规划智能体  │ │  酒店规划智能体  │
│  AttractionAgent │ │    FoodAgent    │ │   HotelAgent    │
│                 │ │                 │ │                 │
│  Chroma RAG     │ │  Chroma RAG     │ │  美团 CLI       │
│  ↓ 不足         │ │  ↓ 不足         │ │  ↓ 失败         │
│  PostgreSQL     │ │  PostgreSQL     │ │  Chroma RAG     │
│  ↓ 不足         │ │  ↓ 不足         │ │  ↓ 不足         │
│  高德 API 拉取  │ │  美团 API 拉取  │ │  seed_poi 拉取  │
└─────────────────┘ └─────────────────┘ └─────────────────┘
         │               │               │
         │   景点规划     │   餐饮规划     │   住宿规划
         │               │               │
         └───────────────┴───────────────┘
                         │
                         ▼
```

---

### 4.3 阶段三：方案决策

```
         景点规划 + 餐饮规划 + 住宿规划
                         │
                         ▼
              ┌──────────────────────┐
              │     方案决策智能体     │
              │     DecisionAgent      │
              └──────────────────────┘
                         │
              ┌─────────┴─────────┐
              ▼                   ▼
        向用户展示候选方案    收集用户选择
              │                   │
              └─────────┬─────────┘
                        ▼
               每日行程定稿
                        │
                        ▼
          已定稿行程（含所有坐标信息）
```

**关键设计：** 方案决策智能体是规划层与执行层之间的**网关**，只有经过用户确认的行程才会进入后续的交通与预算计算，避免无效计算。

---

### 4.4 阶段四：交通规划

```
              已定稿行程
                   │
                   ▼
        ┌──────────────────────┐
        │    交通规划智能体      │
        │    TrafficAgent       │
        └──────────────────────┘
                   │
      ┌────────────┴────────────┐
      ▼                         ▼
┌──────────────┐      ┌──────────────────┐
│  大交通规划   │      │   市内交通规划    │
│              │      │                  │
│ 出发地→目的地 │      │ Day1: 酒店→景点A  │
│ 目的地→酒店   │      │      →景点B→餐厅  │
│ 酒店→返程    │      │      →景点C→酒店  │
│              │      │ Day2: ...         │
└──────────────┘      └──────────────────┘
      │                         │
      └────────────┬────────────┘
                   ▼
          完整交通方案
                   │
                   ▼
```

---

### 4.5 阶段五：预算核算

```
   景点门票费用 + 餐饮费用 + 住宿费用 + 交通费用
                         │
                         ▼
              ┌──────────────────────┐
              │      预算智能体        │
              │     BudgetAgent        │
              └──────────────────────┘
                         │
```

## 5. 数据层设计

### 5.1 向量数据库（Chroma + BGE）

| 属性 | 说明 |
|:---|:---|
| **数据库** | Chroma |
| **Embedding 模型** | BGE（BAAI General Embedding） |
| **存储内容** | 景点、餐厅、酒店的向量化描述文本 |
| **检索方式** | 语义相似度搜索（Top-K） |
| **作用** | 基于用户偏好的语义匹配，实现智能推荐 |

**数据索引流程：**

```
原始数据（名称 + 描述 + 标签）
         │
         ▼
   BGE Embedding
         │
         ▼
   Chroma 向量存储
         │
         ▼
   用户偏好文本 → BGE Embedding → 向量相似度检索 → Top-K 结果
```

---

### 5.2 关系数据库（PostgreSQL）

| 属性 | 说明 |
|:---|:---|
| **数据库** | PostgreSQL |
| **存储内容** | POI 结构化数据（名称、评分、价格、地址、经纬度、标签等） |
| **作用** | ① 为向量检索结果补充坐标等结构化字段；② 作为向量库缺失时的兜底查询 |

---

### 5.3 数据兜底策略

三级兜底机制确保推荐结果不为空：

```
第一级：Chroma RAG（向量语义搜索）
              ↓ 候选 < 3 条
第二级：PostgreSQL 关系库查询
              ↓ 候选 < 3 条
第三级：外部 API 拉取（高德 / 美团 / 其他）
              ↓
         数据入库 → 重新检索
```

| 智能体 | 第一级 | 第二级 | 第三级 |
|:---|:---|:---|:---|
| 景点规划 | Chroma 语义搜索 | PostgreSQL 坐标补全 | 高德 API / seed_poi |
| 美食规划 | Chroma 语义搜索 | PostgreSQL 详情补全 | 美团 API / seed_poi |
| 酒店规划 | 美团 CLI（优先） | Chroma 语义搜索 | seed_poi 拉取 |

## 7. 通信与协作机制

### 7.1 智能体间通信协议

智能体间通过**标准化 JSON 消息**进行通信，消息格式如下：

```json
{
  "message_id": "uuid",
  "from_agent": "agent_name",
  "to_agent": "agent_name",
  "message_type": "request | response | notification",
  "payload": { ... },
  "timestamp": "ISO-8601"
}
```

**通信模式：**

| 模式 | 场景 | 示例 |
|:---|:---|:---|
| **请求-响应** | 同步调用，等待结果 | 方案决策智能体请求交通规划 |
| **发布-订阅** | 广播消息给多个消费者 | TravelParams 并行分发给三种规划智能体 |
| **人机交互** | 需要用户确认的中间状态 | 方案决策智能体向用户展示选项 |

---

### 7.2 错误处理与重试

| 智能体 | 错误场景 | 处理策略 |
|:---|:---|:---|
| 用户交流 | LLM 调用失败 | 3 次指数退避重试 |
| 景点规划 | LLM 调用失败 | 3 次重试 + seed_poi 后重搜 |
| 美食规划 | LLM 调用失败 | 3 次重试 |
| 酒店规划 | LLM 调用失败 | 3 次重试 + 美团 CLI 120s 超时 |
| 酒店规划 | 美团 CLI 超时 | 降级至 Chroma RAG |
| 交通规划 | 高德 API 失败 | Haversine 估算兜底 |
| 预算智能体 | 无（纯计算） | 无需重试 |

## 9. 扩展性设计

### 9.1 新增智能体接入

新智能体只需实现标准接口即可接入现有流水线：

```python
class BaseAgent(ABC):
    @abstractmethod
    def receive(self, message: AgentMessage) -> AgentMessage:
        """接收上游消息，返回处理结果"""
        pass

    @abstractmethod
    def get_capabilities(self) -> List[str]:
        """声明自身能力列表"""
        pass
```

### 9.2 可扩展场景

| 扩展方向 | 新增智能体 | 接入位置 |
|:---|:---|:---|
| 天气适配 | `WeatherAgent` | 阶段二并行（与三种规划并行） |
| 纪念品推荐 | `SouvenirAgent` | 阶段五之后（预算核算完成后） |
| 路线优化 | `RouteOptimizerAgent` | 阶段三与四之间（决策后优化顺序） |
| 冲突检测 | `ConflictDetectorAgent` | 最终输出前（检测时间/预算冲突） |
| 签证/证件 | `VisaAgent` | 阶段一之后（出境游场景） |
