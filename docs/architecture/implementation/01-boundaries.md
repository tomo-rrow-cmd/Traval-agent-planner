# 产品、模块与 Agent 边界

本文件提炼 V1.0/V2.0 产品阶段、后端模块和多智能体编排边界。

## 1. 产品阶段边界

### V1.0 范围

V1.0 聚焦“智能旅行规划方案自动生成”：

- 通过自然语言收集用户出行需求。
- 生成交通、住宿、景点、美食、天气、预算、路线、纪念品等维度的旅行规划。
- 支持方案查询、修改、导出、分享等规划类能力。
- 支持多轮对话、方案生成进度反馈和基础用户偏好。

### V2.0 范围

V2.0 才进入“全流程执行”：

- 票务、酒店、餐厅、景点门票预订。
- 支付、退款、订单、对账。
- 出行中实时提醒、动态调整、旅行助手。
- 微服务化、服务注册发现、消息队列、分布式事务等复杂基础设施。

未明确要求时，V1.0 不实现真实交易、支付、库存扣减和订单履约，只预留接口边界。

## 2. 总体架构

系统采用七层架构：

1. 客户端层：Web/H5 为优先入口，小程序和 App 作为后续扩展。
2. 接入层：Nginx/API 网关、认证鉴权、限流、熔断、日志。
3. 业务服务层：用户、认证、对话、方案、配置、基础数据等 REST API。
4. 智能体编排层：中央协调器、任务调度、状态管理、冲突检测、方案整合。
5. 智能体层：各专业 Agent 执行领域规划任务。
6. 服务能力层：LLM、地图、天气、数据查询、算法工具、格式转换。
7. 数据存储层：PostgreSQL、Redis、向量数据库、对象存储。

V1.0 默认采用模块化单体架构；模块边界要清晰，便于 V2.0 渐进拆分。

## 3. 后端模块边界

推荐后端分层：

- `api/`：路由、鉴权依赖、请求校验、响应封装。不得包含复杂业务逻辑。
- `schemas/`：Pydantic 请求、响应、智能体输入输出模型。
- `services/application/`：业务应用服务，封装用户、对话、方案等用例，API 层不得直接拼业务结果或访问数据库。
- `services/data|llm|map|weather|vector|third_party/`：服务能力层和第三方服务封装。
- `agents/`：智能体实现、Agent 基类、工具注册、专业规划逻辑。
- `orchestrator/`：LangGraph 工作流、全局状态、节点、规划器、冲突检测。
- `db/`：数据库会话、ORM Model、Repository/DAO、迁移相关。
- `utils/`：日志、缓存、安全、通用校验等无业务归属的工具。

依赖方向只能由上层调用下层：

```text
api -> services/application -> orchestrator/agents/services/* -> db/utils
```

禁止事项：

- API 层直接调用数据库。
- Agent 直接访问 ORM Session 或直接调用第三方 SDK。
- Service 层反向依赖 API 层。
- 编排层绕开 Agent 接口直接修改某个 Agent 的内部实现。

## 4. 多智能体架构

中央协调器负责完整规划流程，不把流程控制散落在单个 Agent 中。

核心职责：

- 任务拆解：把用户需求拆成各专业 Agent 可执行任务。
- 调度分发：按依赖关系串行或并行执行。
- 状态管理：维护 `PlanContext` 和规划状态机。
- 冲突检测：处理时间、位置、预算、营业时间等冲突。
- 协调优化：触发相关 Agent 重新生成或局部修正。
- 结果整合：生成按天组织的完整方案。
- 异常处理：超时、重试、降级、失败标记。

规划主流程：

```text
需求收集 -> 信息完整性校验 -> 并行领域规划 -> 冲突检测 -> 路线/预算优化 -> 方案整合 -> 流式输出/持久化
```

专业 Agent 范围：

- 用户交互 Agent：需求理解、追问、偏好抽取。
- 景点规划 Agent：景点候选、游览时长、开放时间、推荐理由。
- 交通规划 Agent：城市间/城市内交通建议、时间和成本估算。
- 美食推荐 Agent：餐厅、菜系、用餐时间、人均消费。
- 住宿推荐 Agent：区域、酒店、价格区间、交通便利性。
- 天气适配 Agent：天气预报、穿搭/活动调整建议。
- 预算管理 Agent：预算拆分、费用汇总、超预算提示。
- 路线优化 Agent：确定性路线算法、时间窗口校验。
- 纪念品推荐 Agent：特产、购买地点、预算建议。

## 5. 状态与通信

- Agent 之间使用“共享上下文 + 消息事件”模式。
- `PlanContext` 是唯一共享状态载体；所有字段应有明确 owner。
- 每次上下文写入必须增加版本或记录变更，便于回溯。
- 同一会话同一时间只允许一个规划任务执行，使用 Redis 分布式锁控制。
- 活跃规划状态优先写 Redis；关键阶段和最终方案必须持久化到 PostgreSQL。
- 系统恢复时从最近稳定阶段继续或回滚重试；无法恢复时标记失败并给用户可理解提示。
