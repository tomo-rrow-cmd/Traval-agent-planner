# 十一、开发规范与工程实践

## 11.1 代码规范

### 11.1.1 Python代码规范

遵循PEP 8规范，使用工具自动检查和格式化。

代码风格：

缩进：4个空格

行宽：最大120字符

命名：变量snake_case，类名PascalCase，常量UPPER_SNAKE_CASE

导入：标准库 → 第三方库 → 本地库，空行分隔

类型注解：所有函数都要有类型注解

代码质量工具：

black：代码自动格式化

isort：导入自动排序

flake8：代码风格检查

mypy：静态类型检查

pylint：代码质量分析

### 11.1.2 前端代码规范

遵循ESLint + Prettier规范

Vue 3 Composition API风格

组件命名PascalCase，变量camelCase

TypeScript类型注解

CSS使用BEM命名规范

### 11.1.3 命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| Python类 | PascalCase | TravelPlanService |
| Python函数/变量 | snake_case | get_user_profile |
| Python常量 | UPPER_SNAKE_CASE | MAX_RETRY_COUNT |
| 数据库表 | snake_case复数 | travel_plans |
| 数据库字段 | snake_case | created_at |
| API路径 | kebab-case | /api/v1/plans |
| 前端组件 | PascalCase | PlanDetail.vue |
| 前端变量 | camelCase | userProfile |

### 11.1.4 注释规范

文档字符串：所有公共类和方法都要有Google风格的docstring

行内注释：复杂逻辑要有行内注释，解释为什么这么做

TODO注释：待办事项用 TODO: 标记，并写清负责人或 Issue、待办内容和完成条件

注释更新：代码修改时同步更新注释，保持一致

### 11.1.5 日志规范

使用结构化日志（JSON格式）

日志级别：DEBUG / INFO / WARNING / ERROR / FATAL

每条日志包含：时间、级别、模块、请求ID、用户ID、内容

敏感信息脱敏，不记录密码、Token等

错误日志保留可定位问题的上下文与完整堆栈，但不得向前端或用户可见内容泄露堆栈、SQL、密钥或第三方原始错误

## 11.3 Git分支管理

### 11.3.1 分支模型

本仓库以 `.agent/conventions.md` 和 `.agent/decisions.md` 为准，采用轻量分支策略。

### 11.3.2 分支说明

| 分支 | 命名 | 用途 | 来源 | 合并到 |
| --- | --- | --- | --- | --- |
| 主分支 | main | 生产环境代码，随时可发布 | - | - |
| 开发分支 | dev | 开发集成分支，功能合并后进入该分支 | main | main |
| 功能分支 | feature/* | 新功能或文档改动 | dev | dev |

约束：

- 不直接向 `main` 推送开发提交。
- 功能开发从 `dev` 创建分支，合并前同步最新 `dev`。
- 仅包含文档、注释、结构快照或协作规范的维护类改动，可在当前分支直接提交；如果当前分支是 `main`，提交前需确认不包含业务代码改动。
- 合并到 `dev` 或 `main` 走 Merge Request/Pull Request；如有对应 Issue，必须在 MR/PR 和提交信息中关联。
- 合并前必须通过 lint、测试和必要的人工 Review。

### 11.3.3 提交规范

提交格式：

```text
<type>: <简述>
<type>: <简述> #<Issue编号>
```

有对应 Issue 时必须使用第二种格式；确实没有 Issue 的小范围文档、配置或整理类提交允许使用第一种格式，但提交说明必须清晰表达变更目的。

类型说明：

| 类型 | 说明 |
| --- | --- |
| feat | 新功能 |
| fix | 修复bug |
| docs | 文档更新 |
| refactor | 代码重构 |

示例：

```text
feat: 新增路线优化智能体 #12
fix: 修复流式输出中断问题 #18
docs: 补充Agent架构边界说明 #21
refactor: 拆分天气服务适配器 #27
docs: 更新文件结构快照
```

若一次提交只是关联但不关闭 Issue，使用 `Refs #12` 写在提交正文；若合并后关闭 Issue，使用平台支持的 `Closes #12`。

### 11.3.4 代码审查

所有代码合并都需要经过Merge Request/Pull Request；如有对应Issue，必须关联对应Issue

至少1人审查通过才能合并

核心模块需要2人审查

CI检查通过才能合并

审查重点：代码质量、安全性、性能、可维护性

## 11.4 CI/CD流程

### 11.4.1 CI/CD工具

当前仓库使用 GitLab CI，流水线入口为 `.gitlab-ci.yml`。现阶段 CI 适配带 `shell` tag 的 GitLab shell runner；更详细的运行说明见 `docs/ci-cd.md`。

### 11.4.2 CI流程

每次提交代码自动触发CI检查。

代码检查：lint检查、类型检查、格式检查

依赖安装：安装项目依赖

单元测试：默认运行离线 pytest 门禁 `python -m pytest -m "not integration" tests`

集成测试：需要真实数据库、第三方 API、LLM Key、向量库或完整 Agent 编排时，使用 `@pytest.mark.integration` 标记并显式运行

安全扫描：依赖漏洞扫描、代码安全扫描

构建镜像：手动任务构建 Docker 镜像；shell runner 本机没有可用 Docker daemon 时跳过

推送镜像：只有 GitLab Container Registry 变量可用时才推送到镜像仓库

默认 CI 不要求真实第三方 API Key 或 LLM API Key。真实密钥仅用于部署环境或显式集成测试环境，并通过 GitLab CI/CD Variables 注入。

### 11.4.3 CD流程

开发环境：`dev` 分支合并后，按仓库实际 CI 配置部署到开发或测试环境

测试环境：需要独立测试环境时，从 `dev` 分支产物部署，并通过环境变量区分配置

生产环境：`main` 分支打 tag 后手动确认部署到生产环境

### 11.4.4 发布流程

功能分支合并到 `dev` 后完成集成验证

从 `dev` 发起到 `main` 的 Merge Request/Pull Request

测试和审查通过后合并到 `main`，打版本 tag

触发生产环境部署

部署完成后进行线上验证

发布分支或热修复分支不是当前默认流程；确需启用时，先更新 `.agent/decisions.md` 并取得团队确认。

### 11.4.5 灰度发布

新版本先发布到少量服务器

观察监控指标，确认没有问题

逐步扩大发布范围，直到全量

出现问题快速回滚

## 11.5 测试策略

### 11.5.1 测试分层

采用金字塔测试模型，不同层级测试各有侧重。

| 测试层级 | 占比 | 测试内容 | 工具 |
| --- | --- | --- | --- |
| 单元测试 | 70% | 函数、类、模块的功能测试 | pytest |
| 集成测试 | 20% | 模块间交互、接口测试 | pytest + FastAPI TestClient |
| 端到端测试 | 10% | 完整业务流程测试 | pytest + HTTP客户端 |

### 11.5.2 单元测试

测试范围：

工具函数

算法逻辑（路线优化、预算计算等）

数据校验逻辑

单个智能体的核心逻辑

覆盖率目标：核心代码覆盖率 > 80%

Mock策略：

第三方API调用全部Mock

数据库操作使用Mock或内存数据库

LLM调用使用Mock，不实际调用大模型

默认 CI 只运行离线测试。需要真实 PostgreSQL/Redis、第三方 API、LLM、向量检索、POI 拉取或真实 Agent 编排的测试必须使用 `@pytest.mark.integration`，默认通过 `pytest -m "not integration" tests` 跳过。

### 11.5.3 集成测试

测试范围：

API接口测试

数据库操作测试

智能体协作流程测试

缓存、消息队列等中间件集成

测试环境：

使用独立的测试数据库

使用独立的Redis库

测试前后自动清理数据

### 11.5.4 端到端测试

测试范围：

完整的方案生成流程

用户注册登录流程

方案分享导出流程

核心场景：

用户发起旅行规划 → 生成完整方案 → 查看方案详情

用户修改方案 → 重新生成 → 方案更新

用户导出方案 → 生成PDF → 下载文件

### 11.5.5 性能测试

压力测试：测试系统在高并发下的表现

负载测试：测试系统在不同负载下的性能

稳定性测试：长时间运行的稳定性测试

工具：locust或jmeter

### 11.5.6 测试执行

本地测试：开发人员本地运行离线测试

CI测试：每次提交自动运行离线测试，不依赖真实第三方服务或本机数据库

回归测试：发布前在准备好外部资源的环境中运行集成测试和完整回归测试

灰度验证：发布后线上灰度验证
