# 多智能体协作旅行规划架构文档

本文档描述 AI 旅行规划系统中多智能体协作的目标架构。该架构围绕“用户自然语言输入 -> 信息结构化 -> 多智能体并行推荐 -> 用户决策确认 -> 交通规划 -> 预算汇总 -> 最终方案输出”的流程展开。

配套 PlantUML 架构图见 [`multi-agent-collaboration.puml`](multi-agent-collaboration.puml)。

## 1. 架构目标

多智能体系统需要解决以下问题：

- 将用户的自然语言旅行需求转化为稳定、可校验、可传递的结构化 JSON。
- 将酒店、景点、美食、交通、预算等专业能力拆分给不同智能体处理。
- 优先使用本地向量数据库和 PostgreSQL 数据库，提高响应速度、稳定性和可控性。
- 当本地数据不足时，通过高德 API、美团 SKILL、12306 等第三方工具补全真实世界信息。
- 在方案确定前持续与用户交互，让用户选择偏好的酒店、餐厅、景点和行程风格。
- 输出包含推荐理由、每日行程、交通路线和预算明细的完整旅行方案。

## 2. 总体架构

系统采用“中央编排 + 专业智能体 + 共享上下文 + 工具调用”的协作模式。

| 层级 | 职责 |
| --- | --- |
| 用户交互层 | 接收用户自然语言输入，追问缺失信息，输出可读答复 |
| 编排层 | 管理流程状态、任务依赖、并行调度、结果汇总和异常降级 |
| 专业智能体层 | 由酒店、景点、美食、方案决策、交通、预算智能体组成 |
| 数据检索层 | 使用 RAG 检索本地向量数据库，使用 PostgreSQL 作为结构化兜底 |
| 工具集成层 | 对接高德 API、美团 SKILL、12306、地图路线、价格查询等外部能力 |
| 结果输出层 | 将最终推荐、路线、预算和注意事项整合为用户可理解的方案 |

## 3. 智能体职责

### 3.1 用户交流智能体

用户交流智能体负责与用户进行自然语言对话，并从对话中抽取旅行相关信息。

核心职责：

- 理解用户的出行意图。
- 抽取出发地、目的地、出行时间、天数、人数、预算、偏好、禁忌、交通偏好等字段。
- 判断信息是否足够进入规划阶段。
- 对缺失字段进行追问。
- 将结构化结果写入全局上下文。

建议输出结构：

```json
{
  "origin": "武汉",
  "destination": "西安",
  "start_date": "2026-08-01",
  "end_date": "2026-08-04",
  "days": 4,
  "travelers": 2,
  "budget": 6000,
  "preferences": {
    "attractions": ["历史文化", "博物馆"],
    "food": ["本地特色", "不吃辣"],
    "hotel": ["交通便利", "中档"],
    "pace": "适中",
    "transport": "公共交通优先"
  },
  "constraints": ["不安排太早出发"],
  "ready_for_planning": true
}
```

### 3.2 景点规划智能体

景点规划智能体根据目的地、时间、偏好和节奏生成每日景点候选。

数据获取顺序：

1. 使用 RAG 从本地向量数据库检索景点语义信息。
2. 当向量检索结果不足时，查询 PostgreSQL 中的景点结构化数据。
3. 当本地数据仍不足、评分过低、坐标缺失或营业信息缺失时，调用高德 API、旅游数据工具等外部服务。

输出内容：

- 每日候选景点列表。
- 推荐理由。
- 游览时长。
- 地址、经纬度、开放时间。
- 门票或预估费用。
- 适配人群和注意事项。

### 3.3 美食规划智能体

美食规划智能体根据用户口味、预算、景点位置和用餐时段推荐餐厅。

数据获取顺序：

1. 使用 RAG 检索本地餐厅、美食、菜系、用户评价等信息。
2. 使用 PostgreSQL 查询餐厅地址、人均价格、标签、评分等结构化字段。
3. 当本地数据不足时，调用美团 SKILL、高德 POI 等第三方工具获取实时或更完整信息。

输出内容：

- 每日早餐、午餐、晚餐或加餐推荐。
- 餐厅名称、菜系、人均价格、地址、经纬度。
- 与当日景点或酒店的位置关系。
- 推荐理由和替代餐厅。

### 3.4 酒店规划智能体

酒店规划智能体根据目的地、预算、入住日期、交通便利性和景点分布推荐住宿。

数据获取顺序：

1. 使用 RAG 检索本地酒店描述、商圈、评价摘要等非结构化信息。
2. 使用 PostgreSQL 查询酒店价格、星级、评分、地址、经纬度等结构化信息。
3. 当本地数据不足或价格时效性不足时，调用美团 SKILL、酒店工具或地图 POI 工具进行补全。

输出内容：

- 酒店候选列表。
- 入住/离店日期、晚数、单晚价格、总价。
- 推荐理由、商圈位置、交通便利性。
- 与主要景点的距离或通勤时间。
- 备选酒店。

### 3.5 方案决策智能体

方案决策智能体负责在酒店、景点、美食三类规划结果之间做用户侧确认和方案收敛。

核心职责：

- 将每日推荐以可比较的方式展示给用户。
- 询问用户对景点、餐厅、酒店、节奏、预算侧重点的具体选择。
- 接收用户的倾向表达，例如“少走路”“更想吃本地菜”“酒店离地铁近一点”。
- 根据用户反馈调整每日行程。
- 解决候选之间的明显冲突，例如同一天地点跨度过大、用餐时间不合理、酒店位置与行程不匹配。
- 输出已确认的每日行程。

方案决策智能体输出的确认结果将作为交通规划和预算汇总的输入。

### 3.6 交通规划智能体

交通规划智能体负责大交通和市内交通两类路线规划。

大交通规划：

- 从出发地到目的地。
- 从到达站点或机场到酒店。
- 返程从酒店到离开站点或机场，再回到出发地。
- 可调用高德路线、12306、航班或其他交通工具。

市内交通规划：

- 酒店到景点。
- 景点之间。
- 景点到餐厅。
- 餐厅到酒店。
- 每日路线总耗时、距离、费用和推荐交通方式。

输出内容：

- 大交通路线。
- 每日市内交通分段。
- 每段交通的起点、终点、方式、耗时、距离、费用。
- 路线风险提示，例如换乘复杂、末班车、拥堵高峰。

### 3.7 预算智能体

预算智能体在所有方案信息确定后执行预算汇总和预算风险判断。

输入来源：

- 酒店智能体输出的住宿费用。
- 美食智能体输出的餐饮费用。
- 景点智能体输出的门票或活动费用。
- 交通智能体输出的大交通和市内交通费用。
- 用户提供的总预算、人均预算或分类预算。

输出内容：

- 总预算、预计总花费、剩余预算。
- 住宿、餐饮、门票、交通、其他费用分类明细。
- 人均费用。
- 超预算风险和调整建议。
- 可选的省钱替代方案。

## 4. 核心数据流

### 4.1 用户意图数据

用户交流智能体将自然语言对话转为 `TravelIntent`。

```json

  "origin": "出发地",
  "destination": "目的地",
  "date_range": {
    "start": "YYYY-MM-DD",
    "end": "YYYY-MM-DD"
  },
  "days": 3,
  "travelers": 2,
  "budget": {
    "amount": 5000,
    "currency": "CNY",
    "scope": "total"

    "food_tags": [],
    "hotel_tags": [],

```

## 5. RAG 与数据兜底策略

酒店、景点、美食三类规划智能体使用统一的数据检索策略。

### 5.1 检索顺序

1. 向量数据库优先：根据目的地、偏好、标签和用户约束做语义检索。
2. PostgreSQL 兜底：查询结构化 POI、价格、评分、坐标、营业时间等字段。
3. 第三方工具补全：当本地数据质量不足时调用外部 API 或 SKILL。
4. 结果融合排序：将本地数据、结构化数据、外部实时数据统一归一化后排序。

### 5.2 信息不足判定

满足任一条件即可触发兜底或第三方查询：

- 向量检索命中数量低于阈值。
- Top-K 结果相似度低于阈值。
- 关键字段缺失，例如地址、经纬度、价格、开放时间。
- 数据更新时间过旧，不适合价格、营业状态等时效性字段。
- 用户需求较特殊，本地数据无法覆盖，例如亲子、无障碍、宠物友好、小众路线。

### 5.3 数据质量标记

所有推荐项建议带上来源和置信度。

```json
{
  "source": ["vector_db", "postgres", "amap"],
  "freshness": "realtime",
  "confidence": 0.91,
  "missing_fields": []
}
```

## 6. 编排流程

### 6.1 主流程

1. 用户与用户交流智能体对话。
2. 用户交流智能体抽取 `TravelIntent` JSON。
3. 编排器检查必要字段是否齐全。
4. 酒店、景点、美食规划智能体并行启动。
5. 三类规划智能体优先检索本地向量数据库，必要时使用 PostgreSQL 和第三方工具补全。
6. 三类规划智能体输出每日候选推荐。
7. 方案决策智能体与用户交互，确认每日具体景点、餐厅、住宿和行程倾向。
8. 编排器将酒店、餐厅、景点、出发地、目的地等位置数据传给交通规划智能体。
9. 交通规划智能体生成大交通路线和每日市内交通路线。
10. 编排器将全部方案信息交给预算智能体。
11. 预算智能体生成预算明细、预算风险和调整建议。
12. 系统输出包含推荐、路线、预算和注意事项的最终旅行方案。

### 6.2 并行与串行关系

| 阶段 | 执行方式 | 说明 |
| --- | --- | --- |
| 信息抽取 | 串行 | 需要先明确目的地、时间、预算等核心字段 |
| 酒店/景点/美食候选 | 并行 | 三类推荐相互独立，可并行提升速度 |
| 方案决策 | 串行循环 | 需要用户确认或表达倾向后才能收敛 |
| 交通规划 | 串行 | 依赖已确认酒店、景点、餐厅和时间顺序 |
| 预算汇总 | 串行 | 依赖所有价格、路线和方案明细 |
| 最终输出 | 串行 | 汇总前序所有结果 |

## 7. 状态管理与通信

智能体之间不直接强依赖彼此，而是通过编排器和共享上下文传递信息。

建议上下文结构：

```json
{
  "conversation": {
    "user_id": "user-001",
    "session_id": "session-001",
    "history": []
  },
  "intent": {},
  "candidates": {
    "attractions": [],
    "restaurants": [],
    "hotels": []
  },
  "decision": {
    "confirmed_itinerary": {},
    "user_choices": [],
    "unresolved_questions": []
  },
  "traffic": {
    "intercity": [],
    "daily_routes": []
  },
  "budget": {},
  "final_plan": {},
  "trace": {
    "agent_runs": [],
    "tool_calls": [],
    "data_sources": []
  }
}
```

通信原则：

- 智能体输入输出必须结构化。
- 每次工具调用需要记录来源、参数摘要、耗时和结果状态。
- 用户确认类信息必须保留原始表达，避免过度归纳导致误判。
- 已确认方案和候选方案分开存储，避免交通和预算使用未确认数据。

## 8. 异常处理与降级

| 场景 | 降级策略 |
| --- | --- |
| 用户信息不足 | 用户交流智能体继续追问，不进入正式规划 |
| 向量检索无结果 | 查询 PostgreSQL，并降低语义匹配权重 |
| PostgreSQL 无可用数据 | 调用高德 API、美团 SKILL 等第三方工具 |
| 第三方接口失败 | 使用缓存、本地结构化数据或返回低置信度候选 |
| 酒店/餐厅价格缺失 | 使用价格区间或历史均价，并标记为预估 |
| 交通路线失败 | 返回可解释的手动补充提示，并保留地点顺序 |
| 预算超支 | 预算智能体给出压缩住宿、餐饮、交通或景点成本的替代建议 |
| 用户迟迟不选择 | 方案决策智能体根据已知偏好生成默认推荐，并明确标记“系统默认选择” |

## 10. 最终输出要求

最终方案建议同时提供结构化 JSON 和面向用户的自然语言摘要。

结构化输出用于前端渲染、地图展示、导出和后续修改；自然语言摘要用于解释推荐逻辑和提醒用户注意事项。

最终方案至少包含：

- 旅行概要：出发地、目的地、日期、天数、人数、预算。
- 每日行程：景点、餐厅、住宿、时间安排。
- 推荐信息：推荐理由、价格、评分、位置、数据来源。
- 大交通路线：出发、到达、返程。
- 市内交通路线：每日分段、方式、耗时、费用。
- 预算明细：分类费用、预计总花费、是否超预算。
- 注意事项：营业时间、天气、拥堵、换乘、价格预估说明。
