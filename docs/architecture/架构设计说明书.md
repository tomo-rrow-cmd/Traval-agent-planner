## 1. 产品概述

### 1.1 产品定位

本产品是一个**面向 C 端用户的智能旅行规划助手**。

用户不需要在多个 App 之间反复切换查询景点、美食、酒店、交通和预算——只需用自然语言说一句"我想去武汉玩三天，预算 3000"，系统即可在几十秒内交付一份包含逐日行程、餐饮安排、住宿推荐、交通路径和预算明细的完整旅行方案。

### 1.2 解决的核心问题

| 用户痛点 | 产品解法 |
|---|---|
| 旅行规划信息分散（查景点用携程、查吃的用点评、查路线用高德） | 一站式整合，一次对话输出完整方案 |
| 规划耗时（手工搜索、比价、排版通常需要数小时） | 多智能体并行规划，几十秒产出方案 |
| 需求不清晰（"想去好玩的地方"但不知道具体是哪） | 智能追问 + 选项引导，帮助用户理清需求 |
| 预算不可控（规划时没概念，结束时超支） | 确定性预算算法，实时核算、超支预警 |
| 方案缺乏弹性（改一个景点就得重排全部） | 局部微调（V2.0），改一处不推翻全案 |

### 1.3 目标用户画像

| 用户类型 | 特征 | 典型需求 | 使用频率 |
|---|---|---|---|
| 效率型 | 上班族、有明确目的地和时间窗口 | "武汉三天两夜，一个人，预算两千" | 中频（每季度） |
| 探索型 | 大学生、没有明确目的地 | "给我推荐一个适合看海的短途旅行" | 低频（寒暑假） |
| 预算型 | 经费有限、对花费敏感 | "长沙两天，最多花 500" | 中频 |
| 家庭型 | 带老人/小孩出行、需要细致安排 | "带 5 岁娃去广州，行程别太赶" | 低频 |

### 1.4 产品边界

**V1.0 做什么**：
- 一次对话生成一份逐日旅行方案（景点 + 美食 + 住宿 + 交通 + 预算）
- 用户通过自然语言描述需求，系统提取并自动规划
- 支持多轮对话补充信息

**V1.0 不做什么**（留给未来版本或外部系统）：
- 不处理实时预订和支付（方案只推荐，不直接下单）
- 不处理多人协作规划（每人设一个会话）
- 不处理跨城市长途自驾路线（当前以市内交通 + 大交通为主）
- 不生成离线 PDF / 打印版行程单

### 1.5 典型使用场景

**场景一：明确目的地**

> 用户："我想去武汉玩三天，从长沙出发，预算三千。"
> 系统：提取参数（武汉/长沙/3天/3000）→ 就绪 → 并行规划 → 返回方案。
> 耗时：约 30-60 秒，用户 0 次表单填写。

**场景二：模糊需求**

> 用户："给我推荐一个适合过周末的地方。"
> 系统：追问"您偏好自然风光还是城市探索？有没有预算限制？从哪个城市出发？"
> 用户逐一回答 → 需求就绪 → 方案生成。

**场景三：预算严格**

> 用户："西安三天，预算 1500，别超。"
> 系统：BudgetAgent 核算实际费用，接近 85% 上限时警告，超支时标注并建议调整。

## 2. 用户使用流程

> **配图**：`diagrams/01-user-journey.puml` — 用户使用主流程活动图

### 2.1 流程概览

用户从打开应用到拿到最终方案，分为 **需求采集** 和 **智能规划** 两大阶段，共 9 个步骤：

```
[需求采集阶段]                     [智能规划阶段]
─────────────────                 ─────────────────
① 登录  →  ② 建会话  →             ⑤ 触发规划
③ 描述需求  →  ④ 补充确认          ⑥ 查看进度
                                        ↓
                                     ⑦ 收到方案
                                        ↓
                                  ⑧ 微调（V2.0）
                                        ↓
                                     ⑨ 确认定稿
```

### 2.2 步骤详解

#### 步骤①：登录

| 项 | 说明 |
|---|---|
| 用户做什么 | 注册账号或输入用户名密码登录 |
| 系统做什么 | JWT 签发令牌，建立用户身份；后续所有请求携带令牌鉴权 |
| 对应需求 | F11.1 / F11.2 / F11.3 |

#### 步骤②：创建会话

| 项 | 说明 |
|---|---|
| 用户做什么 | 点击"新建规划"或类似入口 |
| 系统做什么 | 创建会话对象，持久化到数据库；建立对话上下文 |
| 用户感知 | 进入一个空白对话窗口，可以开始输入 |
| 对应需求 | F10.1 / F10.2 |

#### 步骤③：描述需求

| 项 | 说明 |
|---|---|
| 用户做什么 | 用自然语言说一句或多句话，描述目的地、出发地、天数、预算、偏好等 |
| 示例 | "我想去成都玩四天，两个人，从武汉出发。想吃火锅、看熊猫，整体预算 5000。" |
| 系统做什么 | UserInteraction 智能体理解对话，提取结构化参数（destination/origin/days/budget/preferences） |
| 用户感知 | 正常对话，不需要填表 |
| 对应需求 | F1.1 / F1.2 |

#### 步骤④：补充确认

| 项 | 说明 |
|---|---|
| 系统做什么 | 检查 4 项必填（目的地/出发地/天数/预算）是否完整。不完整则追问；模糊则给选项引导（V2.0） |
| V1.0 行为 | 追问缺的字段，如"请问您计划玩几天？预算大概是多少？" |
| V2.0 增强 | 给出可点击的选项按钮（如"3天 / 5天 / 7天"），降低输入成本（F1.5）；模糊语义给选项确认（如"好玩的地方"→"自然风光 / 人文历史 / 都市繁华"）（F1.6） |
| 循环 | 用户可多轮对话持续补充，每次回复后系统重新检查完整性 |
| 对应需求 | F1.3 / F1.4 / F1.5 / F1.6 |

#### 步骤⑤：触发规划 —— 就绪检测

| 项 | 说明 |
|---|---|
| 触发条件 | 4 项必填信息（destination/origin/days/budget）全部收集完毕 → `ready=true` |
| 系统做什么 | 自动进入五阶段智能规划流水线（无需用户手动点"开始"） |
| 用户感知 | 对话界面显示"开始规划您的旅行..."提示，切换为进度展示模式 |
| 对应需求 | F8.1 |

#### 步骤⑥：查看进度 —— 流式反馈

| 项 | 说明 |
|---|---|
| 系统做什么 | 按阶段实时推送进度事件：并行规划（22%）→ 方案决策（44%）→ 交通规划（66%）→ 预算核算（88%）→ 完成（100%） |
| 用户感知 | 进度条或阶段标签跳动，如"景点规划中...美食规划中...交通计算中..." |
| 如果出错 | 推送错误事件，告知用户"某某环节异常，可以重试" |
| 对应需求 | F9.2 |

#### 步骤⑦：收到方案

| 项 | 说明 |
|---|---|
| 系统做什么 | 输出最终方案（final_plan），包含行程名、概览、逐日行程、交通信息、预算明细 |
| 用户感知 | 看到一份结构化的完整旅行方案，可以上下滚动阅读 |
| 对应需求 | F7.5 / F9.3 |

#### 步骤⑧：微调方案（V2.0）

| 项 | 说明 |
|---|---|
| 用户做什么 | 对方案不满意时，用自然语言提出修改："第二天下午太累了，换个近点的咖啡馆" |
| 系统做什么 | 精准定位要修改的行程节点，局部重算（而非推倒全部重来），返回更新后方案 |
| 用户可修改的范围 | 增删景点、调整顺序、更换餐厅/酒店、调整时间安排 |
| 不能修改的范围 | 一次微调后不会改变目的地、天数、总预算等全局参数（除非用户明确修改） |
| 对应需求 | F5.4 |

#### 步骤⑨：确认定稿

| 项 | 说明 |
|---|---|
| 用户做什么 | 对方案满意后确认 |
| 系统做什么 | 保存最终版本，标记会话状态为已完成 |
| 后续 | 用户可在历史会话中回看方案 |

### 2.3 异常场景处理

| 异常 | 系统行为 | 用户感知 |
|---|---|---|
| 网络中断 | 前端提示"连接已断开"，支持重连后恢复 SSE 流 | 看到错误提示，可重试 |
| LLM 调用失败 | 3 次指数退避重试；3 次都失败则返回错误 | 看到"AI 服务暂时不可用" |
| 外部数据服务不可用 | 自动降级（美团→向量库，高德→直线估算，12306→跳过） | 方案仍能生成，但标注"部分数据为估算值" |
| 数据不足（POI 候选 < 3） | 自动触发 seed_poi 脚本拉取入库后重搜 | 无感知，规划可能稍慢 |
| 预算严重超支 | 在方案中红色标注超支项，建议调整 | 看到明显警告提示 |

## 3. 产品功能架构

> **配图**：`diagrams/02-product-functions.puml` — 产品功能架构组件图

产品功能按用户感知程度和职责分为四层。用户直接接触上面三层，基础服务层对用户不可见。

### 3.1 层次总览

```
┌─────────────────────────────────────────────────────────┐
│                    方案输出层                             │
│    流式进度 · 完整方案 · 来源标注 · 备选方案 · 跳转链接     │
├─────────────────────────────────────────────────────────┤
│                    智能规划层                             │
│  景点推荐 · 美食推荐 · 住宿推荐 · 方案决策 · 交通规划      │
│              预算核算 · 天气联动                          │
├─────────────────────────────────────────────────────────┤
│                    用户交互层                             │
│  对话管理 · 需求采集 · 选项引导 · 模糊确认 · 行程微调      │
├─────────────────────────────────────────────────────────┤
│                    基础服务层（用户不可见）                 │
│              用户鉴权 · 会话管理 · 数据服务                │
└─────────────────────────────────────────────────────────┘
```

### 3.2 用户交互层

> 用户直接使用的功能入口，是产品的"对话界面"。

| 功能 | V1.0 状态 | 说明 | 对应需求 |
|---|---|---|---|
| 对话管理 | ✅ 已实现 | 多轮对话，加载最近 50 条历史维持上下文 | F1.1 / F1.4 |
| 需求采集 | ✅ 已实现 | 从自然语言中自动提取目的地/出发地/天数/预算；识别缺失项并追问 | F1.2 / F1.3 |
| 选项引导 | 🔸 V2.0 | 询问偏好时给出可点击选项按钮（如"自然风光/人文历史/都市繁华"），降低输入成本 | F1.5 |
| 模糊确认 | 🔸 V2.0 | 用户表达模糊时（"好玩的地方""不太贵的"），系统给出具体选项让用户确认 | F1.6 |
| 行程微调 | 🔸 V2.0 | 支持自然语言局部修改方案，精准定位修改范围，局部重算而非推翻全案 | F5.4 |

### 3.3 智能规划层

> 用户需求就绪后，系统内部自动执行的核心规划能力。用户看不到每个智能体，但能感知"规划很快、方案很全"。

| 功能 | V1.0 状态 | 说明 | 对应需求 |
|---|---|---|---|
| 景点推荐 | ✅ 已实现 | 基于目的地语义检索热点景点，排序后按天分配，每项附带推荐理由 | F2.1-F2.4 |
| 美食推荐 | ✅ 已实现 | 检索当地餐厅，分配每日午餐和晚餐，附带推荐理由 | F3.1-F3.3 |
| 住宿推荐 | 🟡 部分 | 优先调用美团获取真实价格评分（120s 超时），降级到向量库检索；**缺 LLM 筛选写推荐理由** | F4.1-F4.4 |
| 方案决策 | ✅ 已实现 | 整合景点+美食+住宿三路结果为逐日行程；景点数量超过阈值时提示用户确认 | F5.1-F5.2 |
| 交通规划 | ✅ 已实现 | 市内交通取高德 API 真实路径（距离/耗时/费用），失败降级直线估算；大交通查 12306；**缺换乘方案和时间缓冲** | F6.1-F6.4 |
| 预算核算 | ✅ 已实现 | 纯确定性算法，按比例分配（住宿35%/交通20%/餐饮20%/门票15%/购物10%）；超支预警；人均日均；组装 final_plan | F7.1-F7.5 |
| 天气联动 | 🔸 V2.0 | WeatherAgent 已实现但未接入编排；接入后可雨天调户外比例、高温安排室内、穿搭提醒 | F14.1-F14.5 |

### 3.4 方案输出层

> 最终呈现给用户的内容和交互。

| 功能 | V1.0 状态 | 说明 | 对应需求 |
|---|---|---|---|
| 流式进度 | ✅ 已实现 | 规划各阶段实时推送进度事件（step_start→progress×4→done） | F9.1-F9.2 |
| 完整方案 | ✅ 已实现 | 输出结构化 final_plan：行程名 + 概览 + 每日行程 + 预算明细 | F7.5 / F9.3 |

## 4. 智能体协作模型

> **配图**：`diagrams/03-agent-collaboration.puml` — 智能体协作业务活动图

本产品核心由 **7 个智能体** 协作完成规划任务。本节从业务视角描述智能体分工和协作方式。

### 4.1 智能体角色总览

| 智能体（角色名） | 类比人类角色 | 核心职责 | 提供什么 |
|---|---|---|---|
| 用户交互智能体 | 旅行顾问 | 和用户聊天，搞清楚需求 | 结构化参数（去哪/从哪出发/几天/预算多少） |
| 景点智能体 | 当地向导 | 找好玩的地方，排好顺序 | 每日景点列表 + 推荐理由 |
| 美食智能体 | 美食博主 | 找好吃的餐厅，分配每顿吃什么 | 每日午晚餐推荐 + 理由 |
| 住宿智能体 | 订房管家 | 找性价比高的酒店 | 酒店推荐（美团真实数据） |
| 方案决策智能体 | 行程策划 | 把景点、吃饭、住宿拼成一天 | 每日完整行程 |
| 交通智能体 | 出行导航 | 算路径、查大交通 | 每段距离/耗时/费用 + 火车票 |
| 预算智能体 | 财务管家 | 算账，别超支 | 费用明细 + 超支预警 + 人均日均 |

### 4.2 协作时序

```
用户交互智能体（第一步）
  │  理解对话 → 提取参数 → 判断就绪
  │  输出：destination, origin, days, budget
  ▼
并行规划（第二步，三个智能体同时工作）
  ├── 景点智能体：找景点 → 排序 → 分天 → 写理由
  ├── 美食智能体：找餐厅 → 分配每顿 → 写理由
  └── 住宿智能体：找酒店（美团优先）→ 推荐
  │  输出：daily_plan, meal_plan, hotel_plan
  ▼
方案决策智能体（第三步）
  │  把三路结果拼成每天的完整行程
  │  输出：每日行程（景点 + 餐饮 + 住宿）
  ▼
交通智能体（第四步）
  │  算每天各段怎么走（高德 API）+ 大交通（12306）
  │  输出：市内交通明细 + 火车票
  ▼
预算智能体（第五步）
  │  按比例分钱 → 核算实际 → 超支警告 → 打包
  │  输出：费用明细 + 最终方案（final_plan）
  ▼
用户查看 / 微调 / 确认
```

### 4.3 为什么这样设计协作

| 设计决策 | 理由 |
|---|---|
| 景点/美食/住宿并行 | 三者没有前后依赖（餐厅不需要等景点定好），同时跑更省时间 |
| 先规划后算账 | 交通和预算都依赖前面的规划结果，必须串行 |
| 预算最后 | 所有花费定下来后统一算总账，才能做超支预警 |
| 预算用算法不用 AI | 算钱要精确，不能靠 AI 猜；超支 1 块钱也是超支 |

### 4.4 数据怎么在智能体间流转

- **共享：** 所有智能体都能读到目的地、出发地、天数、预算、用户偏好
- **产出：** 每个智能体产出结构化数据（景点列表、餐厅列表、酒店列表），存到共享空间中
- **消费：** 后续智能体从前序智能体的产出中取数据（如交通智能体从景点列表中取每天的定位坐标）
- **覆盖：** 微调时（V2.0），方案决策智能体可以局部覆盖之前的产出，不需要全部重跑

### 4.5 扩展智能体（V2.0 接入）

三个智能体已实现但未接入当前协作流程，后续版本接入：

| 智能体 | 接入位置 | 接入后增强什么 |
|---|---|---|
| 天气智能体 | 并行规划之前 | 根据天气预报调整景点推荐（雨天降户外比例、高温安排室内、穿搭提醒） |
| 路线优化智能体 | 方案决策之后、交通规划之前 | 用算法优化每日景点的游览顺序，减少绕路 |
| 纪念品智能体 | 预算核算之前 | 补充购物推荐和价格参考 |

## 6. 产品数据全景

本节从产品角度描述数据从哪来、怎么用，不涉及数据库表结构等技术细节。

### 6.1 数据来源总览

| 数据类别 | 来源 | 获取方式 | 用途 |
|---|---|---|---|
| 景点 | Chroma 向量库 + 外部拉取 | 语义检索 → 不足时自动拉取 | 景点推荐 |
| 餐厅 | Chroma 向量库 + 外部拉取 | 语义检索 → 不足时自动拉取 | 美食推荐 |
| 酒店 | 美团 CLI（优先）+ Chroma（兜底） | 美团真实价格评分 → 失败则向量检索 | 住宿推荐 |
| 市内交通 | 高德 Direction API | 实时 API 查询 | 每段距离/耗时/费用 |
| 大交通 | 12306 | 查询火车票 | 去程/返程火车票信息 |
| 天气 | 和风天气 API | 实时 API 查询 | 天气联动（V2.0） |
| 用户数据 | 用户输入 | 对话提取 | 需求参数 |
| 对话历史 | PostgreSQL | 持久化存储 | 多轮上下文 |

### 6.2 数据保障机制

当数据源不可用时，系统自动降级，保证方案仍能生成（只是可能精度略降）：

```
美团酒店 → 超时/失败 → Chroma 向量库检索
高德交通 → 失败 → 直线距离估算（Haversine 公式）
12306   → 失败 → 跳过大交通，方案仍可输出
Chroma  → 候选不足 → 自动触发外部拉取后重搜
```

| 4 | 行程微调 | 高 | F5.4 | 需 DecisionAgent 支持局部重算 | 避免改一处推翻全案 |
