## 2. 系统概述

### 2.1 项目定位

AI Travel Planner 是一个多智能体协作的 AI 旅行规划系统。用户以自然语言对话描述旅行需求，系统通过 13 个专职 AI Agent 协同工作，经 LangGraph 编排的 8 节点管线，生成包含景点、餐饮、住宿、交通、预算的完整旅行方案，并支持旅行中的行程执行与旅行后的游记生成。

### 2.2 核心功能

- **对话式交互** — 自然语言对话，自动抽取规划参数，多轮确认
- **智能方案生成** — 多 Agent 协同完成景点筛选、餐厅推荐、酒店匹配、交通规划、预算核算
- **方案管理** — 查看、修改、重新生成、导出（Markdown / DOCX / PDF）、分享
- **行程执行** — 签到打卡、花费追踪、实时进度、异常检测与动态调整
- **游记生成** — 基于签到数据自动生成多风格游记与社交分享素材

## 3. 架构总览

### 3.1 分层架构

系统采用严格的七层单向依赖架构。上层可调用下层，下层不可反向依赖上层。

```
API 层 (FastAPI) — app/api/router.py  app/api/v1/*.py
  路由注册、异常处理、依赖注入、SSE 流式响应
        │
        ▼
编排层 (LangGraph) — app/orchestrator/graph.py nodes.py state.py
  8 节点管线、条件路由、重试循环
        │
        ▼
Agent 层 — app/agents/base.py  app/agents/*.py
  13 个专职智能体，各自负责旅行规划的一个子领域
        │
        ▼
服务能力层 — app/services/
  LLM / RAG / 地图 / 天气 / 第三方集成
        │
        ▼
数据层 — app/db/models/  app/db/repositories/
  SQLAlchemy async + ChromaDB + Redis（预留）
```

依赖方向严格单向，上层调用下层，禁止反向依赖。

### 3.2 核心请求全流程

以一个典型请求"从武汉出发去北京玩3天，预算5000"为例：

```
POST /api/v1/chat/sessions/{id}/messages
  │
  ├─ Step 1: 保存用户消息到 DB（幂等去重）
  ├─ Step 2: 加载历史消息（最近 50 条）
  │
  ├─ Step 3: UserInteractionAgent.stream_response()
  │    ├─ LLM 分析完整对话 → 抽取结构化参数
  │    ├─ 必填参数不齐 → 逐项追问
  │    ├─ 参数齐全 → 发确认消息
  │    └─ 用户确认 → ready=True
  │
  ├─ Step 4: run_pipeline() [LangGraph 8 节点]
  │    ├─ parallel_planning: AttractionAgent + FoodAgent + HotelAgent 并行
  │    ├─ decision_r1:       DecisionAgent 贪心选景点+餐厅
  │    ├─ detail_enrich:     DetailAgent 深度补全
  │    ├─ decision_r2:       DecisionAgent 选最优酒店
  │    ├─ plan_traffic:      TrafficAgent 酒店区位评估 + 12306 大交通
  │    ├─ budget:            BudgetAgent 预算核算 + 最终方案
  │    └─ [可选] adjust → 回到 parallel_planning 重跑（超支≤30%）
  │
  ├─ Step 5: 持久化方案摘要 → conversation_plan_runs
  └─ Step 6: SSE 实时推送进度 → 前端渲染
```

### 3.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| Agent 编排 | LangGraph StateGraph | 有向图天然表达规划管线，State 节点间共享，支持条件路由和重试循环 |
| 实时通信 | SSE（非 WebSocket） | 规划是单向流式推送，SSE 更轻量，前端 EventSource 原生支持 |
| 向量检索 | Chroma（本地持久化） | 轻量零配置，单机够用 |
| 数据库双模 | SQLAlchemy async + SQLite/PostgreSQL | 开发零依赖，生产仅改连接串 |
| LLM 多 Provider | OpenAI 兼容抽象 | DeepSeek/豆包/千问统一接口，切换仅改 .env |
| Embedding | BGE-M3 1024维 | 中英文表现好，本地缓存离线可用 |

## 4. 数据库设计

### 4.1 表结构总览

系统共 12 张业务表，分为四组：

**核心业务表（5 张）：** users, conversations, messages, conversation_plan_runs, plans

**基础数据表（3 张）：** attractions, restaurants, hotels

**行程执行表（4 张）：** trip_states, checkins, expense_records, adjustments

### 4.2 核心业务表

**users — 用户表**

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | UUID PK | — | |
| phone | VARCHAR(20) | UNIQUE, INDEX | 手机号 |
| username | VARCHAR(50) | UNIQUE | 用户名 |
| email | VARCHAR(100) | UNIQUE | 邮箱 |
| hashed_password | VARCHAR(255) | NOT NULL | bcrypt 哈希 |
| nickname | VARCHAR(50) | DEFAULT "旅行者" | 显示昵称 |
| avatar | VARCHAR(500) | — | 头像 URL |
| preferences | JSON | DEFAULT {} | 用户偏好 |

**conversations — 会话表**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID PK | — |
| user_id | VARCHAR(36), NULLABLE | 匿名会话可为空 |
| title | VARCHAR(200) | 自动生成 |
| status | VARCHAR(20) | active / completed / archived |
| destination | VARCHAR(100) | 目的地 |
| days | INTEGER | 天数 |

**messages — 消息表**

| 字段 | 类型 | 说明 |

| id | UUID PK | — |

| sequence | INTEGER | 递增序号 |

默认加载最近 50 条，不自动清理更早消息。

**conversation_plan_runs — 会话方案版本表**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID PK | — |

每次成功生成方案新增一行，不覆盖历史版本。`summary` 为方案结构化唯一来源，消息历史 API 在响应阶段补充 summary。

**plans — 旅行方案表**

| 字段 | 类型 | 说明 |

| user_id | FK → users.id | — |

| start_date / end_date | DATE | — |
| budget | FLOAT | 总预算 |
| travelers | INTEGER | 出行人数 |

### 4.3 基础数据表

三张表结构相似，均含 `name, city, category, latitude, longitude, address, rating, image_url, description` 等标准字段，以及 `source, source_poi_id` 联合唯一约束用于稳定外部身份。

| 表 | 特有字段 |
|----|---------|
| attractions | price(门票), opening_hours, recommended_duration, tags(JSON) |
| restaurants | cuisine(菜系), avg_price(人均), opening_hours, tags(JSON) |

数据来源：`scripts/seed_poi.py` → 高德 POI 搜索 → 写入 PostgreSQL → Embedding → 写入 Chroma。

### 4.4 行程执行表

**trip_states — 行程执行状态**

| 字段 | 说明 |
|------|------|
| plan_id | FK → plans.id |

| last_lat / last_lng | 最后签到位置 |

控制流：`active → paused → active → completed/abandoned`，不做复杂状态转移判定。

**checkins — 签到记录**

| 字段 | 说明 |
|------|------|
| poi_type, poi_name, poi_id | 签到目标 |

| time_delta_min | 偏差分钟数 |
| planned_cost vs actual_cost | 预算 vs 实际 |
| rating (1-5), note | 用户感受 |

**expense_records — 花费记录**

| 字段 | 说明 |
|------|------|
| category | 住宿 / 交通 / 餐饮 / 门票 / 购物 / 其他 |
| amount | 实际金额 |

| checkin_id | 可选关联签到 |

**adjustments — 调整记录**

| 字段 | 说明 |
|------|------|
| trigger_type | weather / time_drift / user_request / budget_alert |
| trigger_detail | JSON 触发详情 |
| original_plan / adjusted_plan | JSON 变更前后对比 |
| status | pending → accepted / rejected / applied |

### 4.5 基础 Mixin

所有模型继承自 `app/db/models/base.py`：

| Mixin | 功能 |
|-------|------|
| UUIDMixin | 主键为 VARCHAR(36) UUID |
| TimestampMixin | 自动维护 created_at / updated_at |
| SoftDeleteMixin | deleted_at + is_deleted 软删除 |

### 4.6 迁移管理

使用 Alembic 管理数据库版本：`alembic revision --autogenerate` 生成迁移，`alembic upgrade head` 执行。当前迁移链包含 `conversation_plan_runs` 建表和 POI `source/source_poi_id` 字段。

## 5. Agent 系统

### 5.1 基类设计

`BaseAgent(ABC)`（`app/agents/base.py`）提供以下通用能力：

```python
class BaseAgent(ABC):
    name: str           # Agent 唯一标识
    description: str    # 说明
    llm: BaseLLM        # LLM 实例
    tools: list[dict]   # 已注册工具定义

    async def call_llm(...)         # 调 LLM，自动重试 3 次（指数退避）
    async def call_llm_with_tools() # Function Calling 调用 + 重试
    def register_tools_from_registry(names)  # 从全局注册表批量注册
    async def execute_tools(messages)        # 工具调用循环（最多 3 轮）
    def validate_output(data, Schema)        # Pydantic 校验 + 默认值兜底
```

### 5.2 Agent 清单与职责

#### 管线内 Agent（参与 LangGraph 编排）

**UserInteractionAgent** — 对话入口
- 意图识别：LLM 分析对话历史，判断 daily_chat 或 travel_planning
- 参数抽取：提取 15 个结构化字段（destination, origin, days, total_budget, reserve_budget, planning_budget, preferences, pace, hotel_star 等）
- 状态机：daily_chat → collecting（逐项追问） → awaiting_confirmation（展示确认） → confirmed（ready=True，触发管线）
- 上下文继承：支持"沿用上次配置，只改目的地"等跨轮次语义
- 正则 + LLM 双通道：正则做本地快速判断，LLM 做深度语义解析

**AttractionAgent** — 景点规划
- RAG 语义检索 → LLM 筛选排序 → 坐标补全（PostgreSQL 模糊匹配 → 高德实时搜索兜底）
- 数据不足时自动触发 `poi_live.live_search_attractions` 高德实时搜索
- 输出：daily_plan（每日景点列表，含坐标、门票、推荐理由）

**FoodAgent** — 美食推荐
- 按城市、菜系偏好、人均预算检索餐厅
- 输出：meal_plan（每日三餐推荐，含餐厅名、人均、推荐理由）

**HotelAgent** — 住宿推荐
- 按城市、星级、每晚预算检索酒店
- 调用美团 CLI 获取实时价格（带 `price_verified` 标记）
- 输出：hotel_plan（候选酒店列表 + meituan_raw 原始结果）

**DecisionAgent** — 两轮确定性决策（不走 LLM）

Round 1（定稿景点+餐厅）：
- 如每日景点 > 4 个 → 触发确认
- 整合景点和餐厅到每日行程

Round 2（交通评分选酒店）：
- 调用 TrafficAgent.evaluate_hotels() 做距离矩阵评估
- 选通勤评分最高的酒店
- 输出：selected（酒店名）、selection_reason（评分理由）

**DetailAgent** — 深度信息补全
- 挑选阈值：景点评分 ≥ 4.3，餐厅评分 ≥ 4.2，各最多扩展 3 个
- 数据源优先级：美团 CLI（60s 超时）→ 高德 POI 兜底 → 无数据跳过不编造
- 输出：attraction_details（tips、famous_spots）、food_details（signature_dishes、user_feedback）

**TrafficAgent** — 交通规划
- 酒店区位评估：候选酒店到各景点的距离矩阵 → 通勤便利度评分
- 城际大交通：12306 火车查询 + 机票信息
- 市内交通：高德路径规划（距离、时间、费用）
- 输出：daily_traffic（每日交通段）、big_traffic（火车/机票信息）

**BudgetAgent** — 预算核算

动态分配算法基于城市等级和用户偏好调整五大类比例：

```
BASE: 住宿 35% | 交通 20% | 餐饮 20% | 门票 15% | 购物 10%

城市系数: 北京 1.4 | 三亚 1.5 | 深圳 1.3 | 武汉 0.9 | ...

偏好调整:
  美食: 餐饮 +8%, 住宿 -8%
  穷游: 住宿 -12%, 门票 +7%
  天数≤2: 交通 +5%, 住宿 -5%
```

- 实际费用 vs 预算比对 → 分类明细 + 超支警告
- 超支 0-30% → should_retry=true → adjust 节点降低参数重跑
- 输出：final_plan（完整方案 JSON）、budget_plan（预算详情）

#### 管线外 Agent（独立调用）

**TripAgent** — 行程执行状态管理
- `start_trip()` — 从 final_plan 提取行程元信息（总打卡目标、按天分布）
- `process_checkin()` — 时间偏差计算（偏差 > 30min 触发 adjust）
- `generate_reminder()` — LLM 生成次日提醒（天气 + 穿衣 + 必备物品）
- `_calculate_progress()` — 综合进度 = POI 完成率 × 50% + 天数进度 × 50%

**TravelogueAgent** — 游记生成 + 社交素材
- `generate()` — 签到记录 → 按天分组 → LLM 润色 → Markdown 游记
- 三种风格：日记风(diary) / 小红书风(xiaohongshu) / 攻略风(guide)
- PhotoOrganizer 子模块：9 宫格生成、每日卡片、精选合集、花费总结
- `annotate_photos()` — AI 标注（caption + tags + 质量评分）

**AdjustAgent** — 动态调整

四种触发类型：weather / time_drift / budget_alert / user_request

```python
# 参数修正硬地板
hotel_budget >= 200
meal_budget >= 50
hotel_star 直降 2 星
```

主编排图中通过 `node_adjust_params` 触发参数修正；天气/时间/用户主动调整场景的完整流程为预留能力。

**WeatherAgent / RouteOptimizerAgent / SouvenirAgent** — 仓库中存在，未挂入当前 planner_graph。不属于每次规划必经阶段。

### 5.3 工具系统

`app/agents/tools/tool_registry.py` 统一管理所有工具的 JSON Schema 和 handler 函数。

| 工具名 | 数据来源 | 用途 |
|--------|---------|------|
| search_attractions | Chroma RAG | 景点语义搜索 |
| search_restaurants | Chroma RAG | 餐厅语义搜索 |
| search_hotels | Chroma RAG | 酒店语义搜索 |
| get_weather | 高德天气 API | 天气查询 |
| get_route | 高德 direction | 路径规划 |
| meituan_travel | mttravel CLI | 酒店/景点/行程实时价 |
| railway_search_* | 12306 | 火车票查询 |

Agent 通过 `register_tools_from_registry(["tool_name"])` 注册，`execute_tools()` 自动走 Function Calling 流程（LLM → tool_calls → 执行 → 回传 → 继续，最多 3 轮）。

### 6.2 PlannerState

| 缓存 | cache_stats |

### 6.3 冲突检测

`app/orchestrator/conflict_detection.py` — `ConflictDetector` 在两轮决策后各执行一次：

| 类型 | 规则 | 级别 |
|------|------|------|
| 时间冲突 | 相邻景点交通时间 > 2h | warning |
| 位置冲突 | 同一天景点直线距离 > 30km | error |
| 预算冲突 | 累计费用 > 总预算 | error |
| 营业时间 | 有营业时间无计划到达时刻 | info |

### 6.4 PlanContext

`app/agents/context.py` — 带版本追踪和字段所有权的共享上下文：

# 字段所有权

restaurants  → FoodAgent
hotels       → HotelAgent
traffic_plan → TrafficAgent

# 每次写入自动递增版本号 + 记录变更日志（最近 100 条）

### 6.5 PipelineCache

`app/utils/pipeline_cache.py` — 同次规划中缓存 RAG 检索、地理编码、路线规划结果，避免重复调用。每个 Pipeline 实例独立，不跨请求共享。

## 8. RAG 检索系统

### 8.1 架构

```text
用户查询 "北京历史人文景点适合亲子"
    │
    ▼
EmbeddingService (BGE-M3, 1024维, ModelScope 缓存)
    │
    ▼
Chroma VectorStore (3 个 Collection)
    ├── attractions
    ├── restaurants
    └── hotels
    │
    ▼
Top-K 召回 (默认 40)
    │
    ▼
RerankerService (BGE-Reranker-Base, 默认取 25)
    │
    ▼
PostgreSQL 补充坐标 (模糊匹配)
    │
    ▼
综合评分: 语义相关度(50%) + 评分(25%) + 标签匹配(15%) + 价格(10%)
    │
    ▼
LLM 排序/筛选/推荐理由 → 最终结果
```

### 8.2 VectorStore API

```python
# 语义搜索
vector_store.search(collection_name, query_embedding, n_results=20, where={"city": "北京"})

# 数据写入
vector_store.upsert(collection_name, ids, embeddings, documents, metadatas)

# 统计
vector_store.count(collection_name)
```

### 8.3 Embedding API

```python
# 单文本 → 向量
vec = await embedding_service.embed_query("北京历史人文景点")  # → list[float] (1024维)

# 批量
vecs = await embedding_service.embed(["文本1", "文本2"])
```

切换到 BGE-M3 后，旧 512 维 collection 需重建：`python scripts/seed_poi.py --city 城市名`。

### 9.2 SSE 协议

规划类接口（chat send message、plan create/modify/regenerate）统一使用 SSE。Content-Type: `text/event-stream`，15 秒 keepalive。

**事件类型：**

| event | 方向 | 说明 |
|-------|------|------|
| step_start | S→C | 阶段开始，{step, label} |
| progress | S→C | 进度，{percent, message} |
| message_delta | S→C | 流式文字，{content_delta, sequence} |
| step_end | S→C | 阶段结束 |
| message | S→C | 完整消息，{role, content, message_type} |
| done | S→C | 完成，{summary, plan_id, session_id, conflicts} |
| error | S→C | 异常，{message} |

### 9.3 统一响应格式

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "request_id": "req_abc123"
}
```

错误码：0 成功，10001 参数错误，20001 未登录，20002 权限不足，50000 服务器错误。

### 9.4 鉴权

双通道：`Authorization: Bearer <JWT>`（注册用户）或 `X-Session-Id: <uuid>`（匿名）。JWT Access Token 2h 有效，Refresh Token 7d。
