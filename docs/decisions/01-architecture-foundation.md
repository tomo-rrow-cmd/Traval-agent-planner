# 架构基础决策

> 索引：[.agent/decisions.md](../../.agent/decisions.md) · 范围：D-001 ~ D-008

## D-001：V1.0 采用模块化单体

- 决策：V1.0 使用模块化单体架构，按领域拆分目录和接口；V2.0 再渐进式拆分微服务。
- 原因：当前阶段更需要快速交付和验证，直接微服务会增加部署、运维和联调成本。
- 影响：代码必须保持清晰模块边界，避免跨层调用和隐式共享状态。

## D-002：后端主栈为 Python + FastAPI

- 决策：后端采用 Python、FastAPI、Pydantic、SQLAlchemy 2.0 async。
- 原因：Python AI 生态成熟，FastAPI 适合异步接口和自动文档，便于和 LangGraph/LangChain 集成。
- 影响：所有 API Schema、Agent 输入输出、配置模型优先使用 Pydantic 定义。

## D-003：多智能体编排采用 LangGraph

- 决策：复杂规划工作流由 LangGraph 承担，中央协调器统一调度。
- 原因：旅行规划存在多阶段、分支、循环、状态恢复和冲突协调，图式状态机比线性 Agent 更合适。
- 影响：不要在单个 Agent 中私自串完整流程；新增 Agent 应通过注册和工作流节点接入。

## D-004：LLM 与确定性算法分工

- 决策：LLM 负责理解、生成、推荐说明和结构化抽取；路线优化、预算统计、时间校验等精确计算使用传统算法。
- 原因：确定性计算需要稳定、可复现、可解释，LLM 容易产生计算错误。
- 影响：涉及金额、时间、距离、可达性、排序约束的核心逻辑必须可测试。

## D-005：模型调用走统一 LLM 服务层

- 决策：DeepSeek、豆包、通义千问等模型统一封装在 LLM 服务层，业务模块和 Agent 不直接调用模型 SDK。当前源码以 DeepSeek 为主模型适配器，豆包和通义千问作为备选适配器保留。
- 原因：便于模型切换、限流、重试、日志脱敏、成本统计和降级。
- 影响：所有 Prompt 和模型参数应集中管理，禁止硬编码散落在业务函数中。

## D-006：数据存储组合

- 决策：PostgreSQL 存业务数据；Redis 为配置/架构预留（当前未接入会话或分布式锁实现）；向量数据库（Chroma）存语义检索数据；本地文件系统存导出产物。
- 原因：不同数据类型的访问模式不同，单一存储无法兼顾事务、性能、语义检索和非结构化文件。
- 影响：不要把长期业务数据只放 Redis，也不要把高频临时状态只落 PostgreSQL。Redis 相关描述不应表述为已接入的生产能力。

## D-007：第三方能力通过适配器隔离

- 决策：地图、天气、LLM、内容安全等外部能力必须通过适配器或服务接口封装。
- 原因：第三方服务存在限流、失败、价格变化和供应商切换风险。
- 影响：适配器需要统一错误转换、超时、重试、熔断和缓存策略。

## D-008：API 使用 REST + SSE

- 决策：普通资源接口使用 RESTful `/api/v1/`；方案生成等耗时流程使用 SSE 或异步任务。
- 原因：REST 便于前后端协作，SSE 适合服务端持续推送生成进度。
- 影响：不要让完整方案生成长期占用普通同步 HTTP 请求。
