    **四、导出功能全链路排查与方案设计**

    *   **一线排查：** 通过 curl 手动验证后端 API 确认 MD 导出正常 → 逐层追踪前端调用链 → 定位到 3 个根因问题
    *   **找到问题 1（Toast 不可见）：** `App.vue` 中未挂载 `<ToastContainer />`，`uiStore.showSuccess/showError` 将通知压入 store reactive 数组但 DOM 未渲染 → 所有 Toast 完全不可见
    *   **找到问题 2（MD 导出误 reject）：** 后端对 MD 格式直接返回 `Response`（纯文本），前端 `http.ts` 拦截器用 `data.code !== 0` 校验 → `data` 为字符串时 `data.code === undefined !== 0` → 误判为业务错误并 reject，从不出现在的下载逻辑
    *   **找到问题 3（异步导出无下载）：** 后端返回 task_id 后存入 `exportTask` state，但全项目无任何轮询（`getTaskStatus`）和下载（`downloadExport`）调用代码，这两个函数定义后无人引用
    *   **形成完整修复方案：** 涉及 4 处修改（App.vue + http.ts + PlanDetailPage.vue + planStore.ts），含 abortPolling 防组件卸载泄漏的安全措施

**四、 遇到的问题与困难**

*   **设计与实现中的挑战：**
    *   **SSE 流式响应的前端复杂性：** 7 种事件类型的解析、异常重试（`MAX_RETRIES`）、AbortController 取消、渐进式方案字段名兼容（attractions vs activities, hotel vs accommodation 等 12+ 种字段名映射）。已通过 `normalizeSSESummary` + `mapSSESummaryToPlan` 双函数实现健壮转换
    *   **深色模式维护成本：** 11 个组件存在硬编码颜色值，排查时需逐个组件走读。已统一迁移到 CSS 变量体系，并将 `dark.css` 设计为按组件模块组织的覆盖模式
    *   **前后端字段名不统一：** SSE summary、PlanResponse、数据库字段三层存在多处命名差异（如 `daily_plan` vs `daily_itinerary`、`meal_plan` vs `food_summary`、`hotel` vs `accommodation`）。已在前端 `normalizeSSESummary` 中做了完整的双向兼容映射
    *   **内容块渲染引擎的扩展性设计：** `BlockRenderer` 需要支持 10+ 种块类型的同时保持可扩展性。采用 `type` + `data` 统一接口，新增块类型只需添加 switch-case 分支和对应组件
*   **技术问题（排查导出功能时发现的）：**
    *   Toast 通知系统未接入 DOM 渲染树，所有用户操作反馈（成功/失败/警告）不可见 → 已纳入修复方案
    *   Axios 响应拦截器对非 JSON 响应做 `data.code` 校验导致误 reject → 已明确修复方案
    *   异步导出任务创建后无轮询/下载串联逻辑 → 已设计完善的 handleExport 重写方案
*   **已尝试的解决方案：** 逐层打点 → curl 独立验证后端 → 阅读 axios 源码确认拦截器行为 → 阅读所有相关组件确定完整修复范围

    *   SSE 流式响应的前端实现模式：fetch + ReadableStream 的逐步解析 + 7 种事件类型的异步分发
*   **对项目或开发流程的思考：**
    *   **设计系统先行：** `tokens.css` 的设计 Token 体系在本周深色模式适配中极大降低了工作量——只需在 `dark.css` 覆盖变量值即可完成 11+ 组件的主题切换。这是一个早期架构决策带来显著复利的例证
    *   **通知系统应在 Sprint 初期验证：** Toast/通知等用户反馈链路是 UX 的"最后一公里"，如果不可见，所有 catch 块的错误提示都形同虚设。建议后续开发在功能完成后的第一件事就是验证通知可见性
    *   **前后端接口契约需要更严格的规范：** 本次导出问题的多个根因都源于前后端对"文件下载 vs JSON API"的接口约定不一致。建议后续在 API 文档中明确标注每接口的响应 Content-Type
*   **自我改进方面：**
    *   在开发新功能时同步编写 Store 级别的单元测试，而非累积到后期补充。mock API 调用的测试能在早期拦截数据流问题，比手工排查效率高一个数量级
    *   多关注"无声错误"——那些 catch 了但没有 UI 反馈的错误（如本次的 Toast）。应当在开发环境做全链路的手动验证，确保每个失败路径都有可见的反馈
