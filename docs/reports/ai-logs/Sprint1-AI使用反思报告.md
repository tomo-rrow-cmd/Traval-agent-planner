## 二、AI 使用场景与效果分析

### 2.1 架构设计与决策 ★★★★★

通过 `.agent/decisions.md` 建立 43 条架构决策（D-001 ~ D-043），由 AI 辅助整理、分类和归档到 `docs/decisions/` 的 5 个专题文件。决策文档从一维列表演进到按「架构基础 / 开发流程 / 外部服务 / 规划管线 / 持久化前端」五维拆分的结构化索引。

**反思**：AI 在架构层面的最大价值不是"做决策"，而是"把决策写清楚"。真正关键的取舍（如 D-004 LLM 不碰确定性计算、D-038 行级锁并发安全）依赖人的经验判断，AI 负责将判断转化为可追溯的文档。

### 2.2 代码生成 ★★★★☆

典型模式：人工描述接口语义 → AI 生成 Pydantic Schema + Router + Service + Repository 四层骨架 → 人工调整关键路径。5 天产出 127 个 Python 文件，服务层拆分（API → Service → Repository）完全由 AI 驱动。

**反思**：AI 在模板化代码上效率极高，但在有副作用的复杂逻辑上容易出错——例如 `persist_plan_result()` 的三合一原子事务，AI 初版漏掉了事务边界。**涉及数据库事务、并发控制、外部 API 调用链的代码，必须用集成测试验收。**

### 2.3 测试编写 ★★★★☆

AI 批量生成测试骨架（fixture、mock、断言结构），人工补充边界值和并发场景。测试从 0 增长到 120+ offline + 3 PostgreSQL concurrent + 43 frontend Vitest。

**反思**：AI 写测试趋向于"验证当前实现的行为"而非"验证正确行为"——如果实现本身有 bug，AI 生成的测试会把 bug 固化为契约。**测试应该由人定义语义契约（什么是对的行为），AI 负责填充（怎么写测试代码）。**

### 2.4 文档生成与维护 ★★★★★

AI 负责日报生成、架构文档起草、API 规范、数据库设计文档编写。跨文档一致性维护表现突出——例如新增 D-038 决策后，AI 同步更新了决策索引、架构导航、API 文档、数据库文档和代码结构快照共 5 个文件。

**反思**：这是 AI 使用体验最好的领域。文档天然适合 AI：规则明确、不需要创造力、但工作量大且易出错。唯一风险是"虚假的完整感"——格式精良但可能漏掉隐性上下文，需人工审核把关。

### 2.5 CI/CD 与工程化 ★★★☆☆

AI 生成 `.gitlab-ci.yml`、`Dockerfile`、`pytest.ini` 等工程配置，经历了 6 次修复提交才稳定运行。

**反思**：这是 AI 表现最弱的领域。CI/CD 配置极度依赖实际运行环境，AI 只能基于通用最佳实践生成配置。**不应让 AI 一次性生成完整 CI 配置后"赌它能跑通"。**

### 2.6 AI 禁飞区 — 手写确定性逻辑 ★★★★★

通过 `.agent/guardrails.md` 明确划定三类禁飞区：确定性计算（金额/时间/距离）、硬编码门禁（阈值/断路器）、状态机分支与循环终止条件。15 个关键函数由人工手写。

**反思**：禁飞区不是不信任 AI——它让 AI 在安全区域内放心发挥，把人的注意力集中在最需要判断力的少数关键函数上。**明确告诉 AI 哪里不能碰，比试图让 AI 在所有地方都做对更有效。**

## 四、核心经验总结

### 4.1 做得好的

1. **人工决策 + AI 执行的分工模式**：人在架构决策、边界条件、安全门禁上做判断，AI 在代码生成、文档维护、测试补充上做执行。
2. **文档驱动 AI 协作**：通过 `.agent/conventions.md` 和 `.agent/decisions.md` 建立协作基线，每次"对齐文档"的提交都在缩小 AI 理解偏差。
3. **禁飞区机制**：15 个关键函数手写，其余交给 AI——review 全部代码的认知负担远高于手写少数关键函数。
4. **日报制度**：每天一份 AI 辅助生成的提交总结报告，让工作进度可追溯、可复盘。

### 4.2 需要改进的

1. **AI 测试的"固化 bug"问题**：改进方案——人先定义 Given-When-Then 语义骨架，AI 再填空。
2. **CI/CD 的盲目信任**：改进方案——CI 配置先在本地环境验证，再提交。
3. **事务边界的隐蔽性**：改进方案——多表写入先由人画出事务边界，再让 AI 生成代码。
4. **架构决策的"过度文档化"**：区分"架构决策"和"项目配置"，前者入 decisions.md，后者入 README 或配置文件注释。

### 4.3 对后续项目的建议

1. **第一天就建立 `.agent/` 规范目录**：conventions.md + decisions.md + guardrails.md + architecture.md
2. **先划定禁飞区再开工**：在 AI 开始写代码前明确哪些函数必须手写
3. **AI 写代码，人写测试契约**：Given-When-Then 由人定义并在 code review 中重点检查
4. **日报用 AI 辅助但人把关**：AI 基于 git log 的数据可靠，但决策原因需要人补充
5. **CI/CD 配置以人的环境为准**：不能直接推送远端碰运气

## 五、结语

5 天 163 个提交、127 个 Python 文件、43 条架构决策——Sprint 1 在 5 位贡献者 + AI 的协作下完成了从零到完整后端基础设施 + 前端骨架的搭建。AI 在这个阶段的表现接近满分：它能快速生成 CRUD 骨架、批量创建文档、维护跨文件一致性——这些都是人的效率瓶颈，却是 AI 的强项。但核心判断——哪些计算不能让 LLM 碰、哪些边界条件必须硬编码、哪些事务必须原子化——仍然且必须由人来做出。

AI 在本项目中扮演的角色不是"替代开发者"，而是"放大开发者"——放大了人的决策力（让每个架构决策都有据可查）、执行力（样板代码零成本生成）和记忆力（文档一致性自动维护）。

**人定边界，AI 填内容；人写门禁，AI 跑流程。**
