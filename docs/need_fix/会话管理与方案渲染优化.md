## 一、会话管理持久化

### 1.1 当前问题

远程后端目前的聊天会话 API 只覆盖了最基本的增删查操作——创建会话、列出会话、删除会话、发送消息、获取消息历史。但缺少两个重要的会话管理操作：重命名和置顶。用户无法给会话起一个有意义的名字（默认标题永远是"新的旅行规划"或"新对话"），也无法将重要会话固定在列表顶部，导致当会话数量增多时很难找到之前的对话记录。

### 1.2 优化思路

在 Conversation 数据库模型上增加一个 `pinned_at` 字段，类型为 DateTime，允许为空。当用户置顶某个会话时，将该字段设为当前时间；取消置顶时设为空。这个字段不仅用于标记置顶状态，还能充当排序键——列表查询时按 `pinned_at DESC NULLS LAST` 排序，未置顶的会话排在被置顶的后面；所有未置顶会话之间再按 `updated_at DESC` 排序以保持最近活跃的在前。

在 API 层面新增两条 POST 路由。一条是 `/chat/sessions/{session_id}/title`，接收 `{"title": "新标题"}` 的 JSON 请求体，调用 Service 层更新会话标题并写入数据库。另一条是 `/chat/sessions/{session_id}/pin`，接收 `{"pinned": true/false}`，切换置顶时间戳。

在 Schema 层面，`ChatSession` 响应模型需要增加一个 `pinned` 布尔字段，用于前端渲染置顶图标。同时 ConversationRepository 的 `list_by_user` 方法需要接受 `page` 和 `page_size` 参数以支持分页，并过滤掉 `status = "deleted"` 的会话（目前的实现使用 `limit=20` 硬编码，`page_size` 参数被忽略，且删除操作只将状态设为 `archived` 未过滤）。

Service 层的 `delete_session` 方法目前将状态设为 `archived`，建议改为 `deleted`，配合列表查询的过滤条件，让删除后的会话不再出现在用户面前。

此外，`list_sessions` 返回的 `message_count` 字段目前被硬编码为 0。实际应该通过 SQL 子查询或聚合函数，统计每条会话关联的消息数量，填充到响应中，这样前端侧边栏才能正确显示"3 条消息"之类的提示。

## 二、方案内容持久化

### 2.1 当前问题

远程后端的 Pipeline 在执行完成后，通过 SSE 的 `done` 事件把方案 summary 推送给前端，但这份数据从未写入 `plans` 表。这意味着用户刷新页面后方案详情完全丢失，`GET /plans/{plan_id}` 永远返回 404。方案只在浏览器内存中存在一小段时间，整个方案列表页也是空的。

同时，SSE `done` 事件之后也没有把方案摘要保存到 `messages` 表中。当前本地仓库有一个折中做法：在 `__PLAN__:` 前缀后拼接 JSON 字符串作为消息内容存入 messages 表，但远程后端完全没有这个逻辑。

此外还有一个严重的数据截断问题。完整的方案 summary 包含 7 天的景点、餐厅、酒店、交通、预算等大量数据，序列化为 JSON 后很容易超过 2000 字符。如果简单粗暴地截取前 2000 字符，JSON 会被从中间切断，变成无效的数据，前端解析失败，用户在前端看到的就是损坏的原始文本而非渲染好的方案。

### 2.2 优化思路

在 Pipeline 的 `done` 事件处理中增加两步持久化操作。第一步，将方案 summary 中的核心字段（`trip_name`、`destination`、`origin`、`days`、`daily_itinerary`、`meal_plan`、`hotel_plan`、`traffic`、`budget`、`content_blocks`）提取成一个紧凑的 JSON 对象，用 `__PLAN__:标题|JSON` 的格式存入 messages 表的 `content` 字段。这样做的好处是去掉了 `big_traffic`（车次数组，动辄几十条记录）、`meituan_hotels` 等冗余数据，使得总长度能控制在 5000 字符以内。如果极端情况下仍然超长，则进一步将 `daily_itinerary` 中每个景点只保留 `name`、`price`、`duration_hours` 三个关键字段，丢弃描述文本。前端 `loadHistory` 加载历史消息时，检测到 `__PLAN__:` 前缀的消息就会解析 JSON、还原为 Markdown 或组件数据。

第二步，调用 `TravelPlanService` 创建一个真实的数据记录插入 `plans` 表。把方案标题（从 `trip_name` 获得）、目的地、日期、预算、出行人数、生成的完整行程明细（`daily_itinerary` 的 JSON 序列化）、预估总花费等字段写入。写入后将 `plan_id` 关联回当前会话的 `plan_id` 字段，这样 `GET /plans/{plan_id}` 就能正常工作，用户刷新页面也不会丢失方案。

## 三、方案内容丰富化

### 3.1 当前问题

远程后端的 Pipeline 已经是多轮迭代的设计，包含 `parallel_planning`（并行搜索景点、美食、酒店）、`decision_r1`（第一轮定稿景点和餐厅）、`detail_enrich`（深度详情扩展）、`plan_traffic`（交通规划含多酒店评估）、`decision_r2`（第二轮选最优酒店）、`budget`（预算核算与最终方案输出）、`adjust`（超预算回调重试）共七个节点。且有 `detail_agent.py` 能从定稿的景点和餐厅中挑出评分最高的前三名，通过美团或高德 API 获取真实详情。

但本地仓库的 Pipeline 被简化成了四步（`parallel_planning` → `decision` → `traffic` → `budget`），`detail_enrich` 节点和 `detail_agent.py` 都缺失了。这导致方案详情页只能展示景点名称、价格、坐标这些基础数据，缺少营业时间、特色菜推荐、注意事项等深度内容。

此外，远程后端还有 `exporter.py` 实现了 MD、DOCX、PDF 三种格式的真实文件导出功能，而本地只是一个返回假 `task_id` 的 stub。`scorer.py` 提供了向量相似度评分优化，可以提高 RAG 搜索结果的排序准确性。

### 3.2 优化思路

将远程仓库中的 `detail_agent.py`、`exporter.py`、`scorer.py` 三个文件复制到本地对应目录。在 `nodes.py` 中新增 `node_detail_enrich` 节点，调用 `DetailAgent`，从已定稿的 `daily_plan` 和 `meal_plan` 中按评分阈值（景点不低于 4.3 分、餐厅不低于 4.2 分）筛选亮点，通过高德的 `search_poi` 或美团的 `search_hotel` 获取真实详情数据，输出 `attraction_details` 和 `food_details` 两个字段。在 `graph.py` 中将该节点插入到 `decision_r1` 和 `plan_traffic` 之间。

导出路由 `POST /plans/{plan_id}/exports` 当前为 stub，改为调用 `exporter.py` 将 `PlanResponse` 数据真实导出为文件并返回二进制下载。Pipeline 的进度百分比也需要从当前粗略的四阶段（25% → 50% → 75% → 95%）对齐到更精细的七阶段（15% → 30% → 45% → 60% → 75% → 92% → 100%），让前端进度条更准确地反映实际进度。

## 四、渲染层重构——块驱动混合渲染

### 4.1 当前问题

方案详情页 `PlanDetailPage.vue` 采用的是"纯组件硬编码布局"——页面模板中按固定顺序调用 `PlanHeader`、`PlanTimeline`、`DayCard`、`BudgetChart`、`PlanMap` 等组件。这种方式的缺陷是：

第一，无法应对方案的多样性。3 天短途和 7 天长途的展示需求不同，有的方案包含了 12306 大交通数据需要展示车次列表，有的方案有超预算警告需要醒目标出——但组件模板写死了顺序，无法按内容有无来动态增删区块。

第二，大量 AI 生成的文本内容（每日行程描述、出行贴士、天气建议、深度攻略）被丢弃了，因为组件只读取结构化字段（如 `title`、`cost`、`duration_minutes`），不管 LLM 写了多么好的文字描述。

第三，"实时方案"右侧面板 `PlanPreview.vue` 和方案详情页 `PlanDetailPage.vue` 是两套独立的渲染逻辑，维护成本高，字段名互相不一致（如 PlanPreview 读 `plan.budget` 而 PlanDetailPage 读 `plan.budget_detail`），容易出现一边正常一边空白的尴尬局面。

### 4.2 优化思路

引入"内容块驱动渲染"（Content Block-based Rendering）。核心思想是：后端在 Pipeline 末端，由 `ContentFormatter` 将 `final_plan` 的全部数据按规则组装成一个有序的内容块列表 `content_blocks`，每个块包含一个 `type`（决定用什么方式渲染）和 `data`（携带该块的数据）。前端只需一个通用的 `BlockRenderer` 组件，按 `type` 分发——`header` 块渲染 Vue 组件，`text` 块渲染 Markdown，`day_card` 块渲染折叠卡片，`budget_chart` 块渲染环形图，`callout` 块渲染图标搭配文字的提示卡片，`divider` 块渲染分隔线。

块类型定义九种：`header`（方案概览头部，含标题、目的地、天数、费用）、`text`（Markdown 文本，用于行程概览描述、交通说明等）、`day_card`（每日行程卡片，含景点列表、餐饮、住宿）、`budget_chart`（预算环形图）、`map`（高德地图标记和路线）、`divider`（视觉分隔线）、`callout`（带图标和颜色的提示卡片，用于深度详情、超预算警告）、`traffic_list`（大交通车次表格）、`list`（标签或清单列表，如行李清单）。

后端 `ContentFormatter` 采用纯规则拼装（不使用 LLM），确保稳定性和零额外延迟。拼装顺序为：方案头部 → 行程概览描述（一段 Markdown 文本，总结目的地、天数、预算等核心信息）→ 逐日行程卡片（每个 `day_card` 内部将 AttractionAgent 输出的 `attractions[]` 数组映射为前端 ActivityItem 组件所需的字段名，即 `name` 对应 `title`、`reason` 对应 `description`、`price` 对应 `cost`、`duration_hours` 换算为 `duration_minutes`、`latitude/longitude` 包装为 `location` 对象）→ 深度详情 callout（如果有 `attraction_details` 数据，为每个详情生成一个 callout 块）→ 大交通车次列表（`big_traffic` 的前 8 条数据，展示车次号、出发站、到达站、时间、票价）→ 市内交通总结（`traffic.daily_traffic` 拼接为 Markdown 文本）→ 预算环形图（将 `budget.details[]` 中的分类花费映射为 `breakdown` 对象，包含交通、住宿、餐饮、门票、购物五个类别的金额）→ 超预算警告（遍历 `budget.warnings[]`，每个警告生成一个 warning 级别的 callout 块）→ 出行贴士（Markdown 格式的无序列表）→ 行李清单（`list` 块，以标签形式展示）→ 地图标记（从 `daily_itinerary` 中提取所有有坐标的景点，生成 marker 数组）。

前端 `BlockRenderer` 组件是一个通用渲染器。它接收 `blocks` 数组作为 prop，用 `v-for` 遍历，根据每个块的 `type` 决定渲染方式：Vue 组件类的块（`header`、`day_card`、`budget_chart`、`map`、`traffic_list`）使用 `v-bind="block.data"` 直接将数据绑定到组件；文本类的块（`text`）使用 MarkdownIt 将 Markdown 字符串渲染为 HTML，通过 `v-html` 注入，配合全局 CSS 实现表格、标题、列表的样式；装饰类的块（`divider`、`callout`、`list`）直接在 BlockRenderer 内用少量 HTML 和 CSS 渲染。

`PlanPreview` 和 `PlanDetailPage` 都会改用 BlockRenderer。区别仅在于 PlanPreview 只取前几个块（`content_blocks` 的前 N 个 day_card 加上 header），PlanDetailPage 展示全部块。两者共用同一套渲染逻辑和字段名，不再需要各自独立维护。

## 五、数据一致性修复

### 5.1 当前问题

`message_count` 在 `list_sessions` 返回中硬编码为 0，导致前端侧边栏始终显示空的消息计数。`list_sessions` 的后端 Repository 方法没有使用入参中的 `page` 和 `page_size`，而是用默认的 `limit=20`，导致分页参数无效。

### 5.2 优化思路

在 `ConversationService.list_sessions` 中，调用 `list_by_user` 后额外执行一条 SQL 聚合查询：按 `conversation_id` 分组统计 `count(id)`，得到一个从会话 ID 到消息数的映射。再将映射填入每个 `ChatSession` 的 `message_count` 字段。`list_by_user` 方法的签名从 `list_by_user(user_id, limit)` 改为 `list_by_user(user_id, page, page_size)`，内部使用 `offset` 和 `limit` 实现正确的分页。

## 六、Pipeline 进度对齐

### 6.1 当前问题

远程后端的 Pipeline 包含七个节点（`parallel_planning`、`decision_r1`、`detail_enrich`、`plan_traffic`、`decision_r2`、`budget`、`adjust`），但 `pipeline.py` 中 `stage_progress` 映射表还是较早版本的四阶段进度（25% → 50% → 75% → 95%），前端进度条显示与实际执行阶段脱节。

### 6.2 优化思路

更新 `stage_progress` 字典，为每个节点分配合理的进度百分比：parallel_planning 占 15%（并行搜索三个阶段中最耗时），decision_r1 占 30%（AI 定稿），detail_enrich 占 45%（API 获取深度详情，网络耗时），plan_traffic 占 60%（交通规划含多酒店高德路线查询），decision_r2 占 75%（选最优酒店），budget 占 92%（预算核算与最终输出），completed 占 100%。这样每个阶段结束时前端进度条都能看到确切进展，用户体验更好。

## 七、改动文件汇总

此次优化共涉及十八个文件的改动。后端模型层一个文件（`conversation.py` 增加 `pinned_at` 字段），路由层两个文件（`chat.py` 增加重命名和置顶路由以及方案持久化和 compact 存储，`plan.py` 改造导出路由），Schema 层两个文件（`chat.py` schema 增加 `pinned` 字段，`plan.py` schema 增加 `ContentBlock` 定义），Repository 层一个文件（`conversation_repo.py` 增加 toggle_pin 方法并改造 list_by_user），Service 层一个文件（`conversation_service.py` 增加 rename 和 pin 方法并改造 list 和 delete），新增后端子模块三个文件（`detail_agent.py`、`exporter.py`、`scorer.py` 从远程仓库复制），新增内容格式化器一个文件（`content_formatter.py`），Pipeline 和编排层两个文件（`pipeline.py` 集成 content_blocks 并对齐进度，`nodes.py` 和 `graph.py` 增加 detail_enrich 节点），前端新增通用渲染器一个文件（`BlockRenderer.vue`），Store 层一个文件（`chatStore.ts` 调整 done 事件处理以适配 content_blocks 和 message_delta），页面层两个文件（`PlanDetailPage.vue` 和 `PlanPreview.vue` 改用 BlockRenderer 替代硬编码布局）。

执行顺序上，先做完会话层的持久化改造（Phase 1），然后做 Pipeline 的持久化和 content_blocks 生成（Phase 2），接着从远程合并 detail_agent、exporter、scorer 三个模块（Phase 3），最后改造前端渲染层（Phase 4）。这种依赖关系保证了每一步完成后的功能都是可测试的，不会出现改动一半前端报错的情况。
