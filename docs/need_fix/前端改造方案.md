# 前端改造方案

> 对应文档：`远程后端优化方案-纯文字版.md`  
> 日期：2026-07-09

---

## 一、核心思路

后端改造完成后，SSE 的 `done` 事件除了原有的 `summary` 外，还会增加一个 `content_blocks` 数组。这个数组是一个有序的内容块列表，每个块包含 `type`（块类型）和 `data`（数据载荷）。前端不再需要硬编码渲染每个组件，而是通过一个通用的 `BlockRenderer` 组件按块类型动态分发渲染。

同时，远端后端 merge 到本地后，还会带来 `detail_agent` 生成的真实详情数据（评分最高的前三名景点的营业时间、注意事项等）、`exporter` 支持的真实文件下载、以及更准确的 RAG 向量搜索评分。

前端改动的核心目标是三个：第一，让 PlanDetailPage 和 PlanPreview 都能用 BlockRenderer 渲染，内容统一且不丢失数据；第二，修复之前发现的 MapContainer 首次加载不画路线、会话切换遗留旧方案、重命名本地状态不同步等已知 Bug；第三，处理好前后端数据格式的差异（SSE summary 的字段名与后端 PlanResponse schema 不一致，需要通过归一化转换）。

---

## 二、新增 BlockRenderer 通用渲染组件

这是前端改动中最重要的部分。BlockRenderer 是一个只负责接收 `blocks` 数组并分发的纯渲染组件，不参与数据获取。

组件接收到 `blocks` 后，用 `v-for` 遍历，根据每个块的 `type` 决定如何渲染。块类型共九种，渲染方式分为三类：

第一类是 Vue 组件类块，直接用 `v-bind` 将 block 的 `data` 对象绑定到子组件的 props 上。`header` 块绑定到 PlanHeader.vue（方案标题、目的地、出发地、天数、预算、费用）；`day_card` 块绑定到 DayCard.vue（每日活动列表、住宿、日花费）；`budget_chart` 块绑定到 BudgetChart.vue（预算环形图的数据）；`map` 块绑定到 PlanMap.vue（地图标记点和路线路径）；`traffic_list` 块在一个简单的内置模板中渲染车次表格（车次号、出发站、到达站、时间、票价）。

第二类是文本类块。`text` 块使用 markdown-it 库的 render 方法，将 data 中的 Markdown 字符串转换为 HTML，通过 `v-html` 注入 DOM。这个 HTML 会继承全局 CSS 中定义好的标题、表格、引用块、粗体、斜体等样式，与聊天气泡中的 Markdown 渲染效果保持一致。

第三类是装饰类块。`divider` 块渲染一条视觉分隔线（`hr` 元素）；`callout` 块渲染一个带图标的提示卡片，根据 `data.level` 的不同值（info、warning、success）显示不同的背景色和左边框颜色，用于展示深度详情内容或超预算警告；`list` 块渲染标签列表（使用 Ant Design Vue 的 `a-tag` 组件包裹每个 `data.items` 中的元素）。

BlockRenderer 对不认识的 `type` 值做容错处理，静默跳过并输出一行控制台警告，不会导致白屏。

## 三、PlanDetailPage 重构

当前 PlanDetailPage 的模板是按固定顺序列出 PlanHeader、PlanTimeline、DayCard、BudgetChart、PlanMap 等组件。在改为 BlockRenderer 后，整个模板简化为两层：第一层是沉浸式的 BlockRenderer 组件（从 `plan.content_blocks` 中拿所有块来渲染），第二层保留一个顶部的 sticky 时间线导航（PlanTimeline 用于快速跳转到某一天）。因为 BlockRenderer 本身已经按线性顺序渲染了所有 day_card 块，PlanTimeline 只作为辅助导航，点击某天时通过 `scrollIntoView` 平滑滚动到对应的 day_card 位置。

数据获取逻辑维持现有设计。首先检查 `planStore.currentPlan` 是否有数据且 `content_blocks` 不为空（说明刚刚通过 SSE 生成、数据还在内存中），如果是就直接用，不发 API 请求。如果不是（说明是刷新页面或从外部链接进入），调用 `planStore.fetchPlanDetail(planId)` 获取方案详情。API 返回的 `PlanResponse` 如果没有 `content_blocks` 字段，PlanDetailPage 需要做兜底：在前端根据 `daily_itinerary`、`budget_detail`、`traffic_summary` 等字段组装出一个简易的 `content_blocks` 列表，再用 BlockRenderer 渲染。这个兜底逻辑可以内嵌在页面中，也可以封装成一个 `buildBlocksFromPlanResponse` 工具函数。

PlanTimeline 仍然从 `plan.daily_itinerary` 中提取天数，因为 `daily_itinerary` 作为 PlanResponse 的结构化字段始终存在，不会因为改用 BlockRenderer 而丢失。

## 四、PlanPreview 改造

右侧实时方案面板的改造思路和详情页类似，但有几个不同点。

首先，PlanPreview 只展示 content_blocks 的缩略子集。具体做法是取 `content_blocks` 中的 `header` 块（标题、目的地、天数、费用概览）和前面的三个 `day_card` 块，再加一个"查看完整方案"按钮。这样用户能在侧面板中看到最关键的信息概览，点击按钮后跳转到 `/plans/:planId` 查看全部内容。这个逻辑在 computed 属性中完成过滤，不会修改 store 中的数据。

其次，PlanPreview 本身有三种展示状态：生成进行中（显示进度条和骨架占位符）、方案就绪（显示 BlockRenderer 缩略）、空状态（显示引导文字）。其中"生成进行中"状态依赖 `planStore.isGenerating` 和 `planStore.generateProgress`，这个逻辑保持不变。"方案就绪"状态现在改为检查 `plan.content_blocks` 是否存在且长度大于零。如果旧方案没有 content_blocks（从历史数据加载的），则使用现有的 fallback：显示目的地、天数、费用统计等简要信息。

最后，PlanPreview 的 `hotel_plan`、`big_traffic`、`traffic` 这些统计字段的读取方式也需要做兼容处理。如果 `content_blocks` 存在，直接从中提取相应块的数据；如果不存在（旧数据），则使用 `plan` 对象上的直接字段。这可以通过一个简单的 computed 属性来屏蔽差异。

## 五、chatStore 核心改造

chatStore 是前端消费 SSE 数据的中枢，需要做三处关键调整。

第一处：`handleSSEEvent('done')` 处理。当 SSE 的 `done` 事件到达时，除了原有的消息推入和 Markdown 生成外，增加对 `content_blocks` 的提取。从 `doneData` 中取出 `content_blocks` 数组，存入 `planStore.currentPlan` 的对应字段。同时利用 `normalizeSSESummary` 函数将 SSE summary 转换为 PlanResponse 兼容格式（这个函数我们已经实现了，但需要在 done 事件和 loadHistory 两个入口都调用）。消息的 `metadata` 中也需要保存 content_blocks 的引用，方便后续恢复。

第二处：新增 `message_delta` 事件处理。当前 `handleSSEEvent` 的 switch 语句中没有 `case 'message_delta'`，导致这些事件落入 `default` 分支并打印大量警告日志。应该增加一个 case，将这些流式增量文本事件静默处理（因为最终的完整文本会在 `message` 事件中体现）。如果将来需要实现打字机效果（逐字流式显示），可以在 `message_delta` case 中追加到当前聊天消息的结尾。

第三处：`loadHistory` 处理。从 API 加载历史消息时，检测到 `__PLAN__:` 前缀的消息后，解析 JSON 并调用 `generatePlanMarkdown` 生成聊天气泡用的 Markdown 字符串，这是已有的逻辑。新增的逻辑是：从解析后的 JSON 中提取 `content_blocks`（如果有的话），存入 `planStore.currentPlan`，这样用户回到旧会话时右侧面板也能正常显示。同时调用 `normalizeSSESummary` 将 summary 转换为 PlanResponse 兼容格式。

## 六、planStore 改造

planStore 的 `normalizeSSESummary` 函数已经实现了 SSE summary 到 PlanResponse 格式的字段名映射。在此基础上需要增加对 `content_blocks` 的处理：如果 summary 中带有 `content_blocks`，直接透传；如果没有（来自旧数据或简化版 SSE），在归一化的同时使用前端工具函数 `buildContentBlocksFromSummary` 生成一份简易的块列表。

planStore 的 `clearCurrentPlan` 方法（已有）用于切换会话时重置方案面板，这个逻辑保持不变。但 `currentPlan` 的类型定义需要从 `PlanResponse | null` 扩展为允许包含 `content_blocks` 的版本，因为 `content_blocks` 不在标准的 `PlanResponse` 类型中——它是 SSE 专用的扩展字段。

## 七、已知 Bug 修复

以下是之前排查出来但尚未完整修复的前端问题，应在本次改造中一并解决。

**MapContainer 首次不画路线**。loadMap 函数中调用了 updateMarkers 来添加地图标记，但没有调用 updatePolylines 来画路线。需要在 updateMarkers 调用后增加一行 updatePolylines 调用。修改位于 public/components/map/MapContainer.vue 的 loadMap 函数中。

**切换会话不清空方案面板**。ChatSessionPage.vue 的 onMounted 和 watch 中只调用了 loadHistory 来加载消息，但没有调用 planStore.clearCurrentPlan 来重置方案面板。需要在加载历史消息之前先清空当前方案，否则切换到新会话时右侧面板仍然显示上一个会话的方案。修改位于 public/views/ChatSessionPage.vue 的 onMounted 和 watch 函数中。

**fetchSessions 合并逻辑 Bug**。当从服务器拉回会话列表后，旧的合并逻辑只把服务器有而本地没有的会话追加进来，已有会话的 title、status、pinned 等字段永远不会被服务器数据更新。这意味着用户重命名会话后，如果 fetchSessions 被调用（例如路由切换触发），本地缓存的旧标题会覆盖服务器返回的新标题。修改方式为：用服务器数据完全替换本地数据中对应 ID 的会话，只保留服务器没有的本地新会话（例如刚刚通过 createSession 创建但后端还没来得及写入的）。

**message_delta 警告日志过多**。在 handleSSEEvent 的 switch 语句中增加 `case 'message_delta':` 分支，静默忽略即可。虽然不影响功能，但几十条黄色警告日志对调试体验很不友好。

## 八、ChatMessage 改造（可选增强）

当前 ChatMessage 有三种渲染模式：`text`（普通 Markdown）、`plan_progress`（进度条）、`plan_result`（方案卡片）。其中 `plan_result` 模式内部嵌入了 `generatePlanMarkdown` 生成的完整 Markdown 渲染，以及一个"查看完整方案"按钮。

如果内容块驱动渲染的方案被采纳，可以考虑在 ChatMessage 中增加一个小型 BlockRenderer 预览。具体做法是：当 message_type 为 plan_result 且 metadata 中有 content_blocks 时，从中提取 `header` 块和前三天的 `day_card` 块，在聊天气泡内做一个紧凑的缩略预览（取代目前占据整个气泡的大段 Markdown）。这个功能是可选的，优先级较低，因为它不影响方案的完整展示，只是一个视觉优化。

## 九、导出和分享的前端支持

后端改造完成后，`POST /plans/{plan_id}/exports` 将返回真实的文件二进制数据而非假 task_id。前端 `api/plan.ts` 中的 `apiExportPlan` 函数需要调整响应处理：根据 `format` 参数的不同（md、docx、pdf），接收对应的 Content-Type 响应头，并在浏览器中触发文件下载。可以使用 URL.createObjectURL 创建一个 Blob URL，通过隐藏的 `a` 标签自动点击触发下载，然后释放 URL。

分享功能 `POST /plans/{plan_id}/shares` 目前已经能正常返回 `share_url` 和 `expire_at`，ShareDialog 组件也实现了基本的剪贴板复制功能，暂不需要改动。

## 十、改动文件清单与依赖关系

本次前端改造涉及七个文件的修改或新建：

第一个是新建文件：BlockRenderer.vue（通用块渲染组件），它是所有后续改动的依赖基础，必须先完成。它位于 frontend/src/components/plan/ 目录下。

第二个是 PlanDetailPage.vue 的改造：模板中用 BlockRenderer 替代硬编码的 DayCard、BudgetChart 等组件；onMounted 逻辑增加 content_blocks 检查和 API 回退兜底。位于 frontend/src/views/ 目录下。

第三个是 PlanPreview.vue 的改造：使用 BlockRenderer 缩略子集替代现有硬编码统计字段。位于 frontend/src/components/plan/ 目录下。

第四个是 chatStore.ts 的改造：done 事件中提取 content_blocks 并调用 normalizeSSESummary，新增 message_delta case，修复 fetchSessions 合并逻辑。位于 frontend/src/store/ 目录下。

第五个是 planStore.ts 的改造：增加 buildContentBlocksFromSummary 兜底函数，normalizeSSESummary 中增加 content_blocks 处理。位于 frontend/src/store/ 目录下。

第六个是 ChatSessionPage.vue 的 Bug 修复：会话切换时调用 clearCurrentPlan。位于 frontend/src/views/ 目录下。

第七个是 MapContainer.vue 的 Bug 修复：首次加载增加 updatePolylines 调用。位于 frontend/src/components/map/ 目录下。

建议执行顺序：先修复 Bug（第六、第七，风险最低），再创建 BlockRenderer（第一，依赖基础），然后改造 Store（第四、第五，数据层），最后改造页面（第二、第三，视图层）。这样每个阶段完成后功能都可以独立验证。
