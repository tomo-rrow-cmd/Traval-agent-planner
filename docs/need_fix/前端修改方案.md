# 持久化机制修复 — 前端修改方案

> **状态：✅ 已应用（2026-07-10）** — 本文档为修复方案的历史记录，所列问题已全部修复并合入主分支。保留本文档供参考修复思路和设计决策。

## 问题概述

前端当前存在以下持久化相关的问题：

1. **方案 Markdown 内容仅存在于运行时内存** — `chatStore.sendMessage()` 收到 SSE `done` 事件后，`generatePlanMarkdown(summary)` 生成的 Markdown 字符串只存储在 `messages.value` 数组中，刷新页面即丢失
2. **`loadHistory()` 依赖已废弃的 `__PLAN__:` 前缀** — 加载会话历史时，通过检查消息 `content.startsWith('__PLAN__:')` 来识别方案结果消息，这是不稳定且已标记为废弃的机制
3. **方案面板在页面刷新后无法恢复** — `planStore.currentPlan` 仅存在于 Pinia 内存中，页面刷新后为 null，必须依赖 `loadHistory()` 通过 `__PLAN__:` hack 来重建

**修复后的流程**：后端会在 `messages` 表中存储 `message_type='plan_result'` 的消息，`content` 为 Markdown，`metadata.summary` 存储完整的方案摘要 JSON。前端只需检测 `message_type` 即可正确识别和恢复方案数据。

## 修改清单

### 1. `loadHistory()` 改用 `message_type` 检测

**文件**: `frontend/src/store/chatStore.ts`

#### 当前问题

`loadHistory()`（约第 240 行）遍历消息列表时，检测 `content.startsWith('__PLAN__:')` 来识别方案结果消息，解析嵌入的 JSON 来重建 Markdown 和 `planStore.currentPlan`。

#### 修改内容

将方案结果检测逻辑从内容前缀检测改为 `message_type` 字段检测：

```typescript
async function loadHistory(sessionId: string, page?: number): Promise<void> {
    try {
      const result = await apiGetMessages(sessionId, { page, page_size: 50 })
      let list: MessageRecord[] = result.data?.list ?? []
      const pStore = usePlanStore()

      for (let i = 0; i < list.length; i++) {
        const m = list[i]

        // 新方案：通过 message_type 识别方案结果消息
        if (m.role === 'assistant' && m.message_type === 'plan_result' && m.metadata?.summary) {
          const summary = m.metadata.summary as Record<string, any>
          // 如果后端已存了 Markdown 直接用，否则客户端生成
          list[i] = {
            ...m,
            content: m.content || generatePlanMarkdown(summary),
            message_type: 'plan_result',
            metadata: { ...m.metadata, summary },
          } as any
          // 恢复实时方案面板
          pStore.currentPlan = {
            ...(pStore.normalizeSSESummary(summary) as any),
            id: m.metadata.plan_id || '',
          }
          pStore.isGenerating = false
          continue
        }

        // 降级兼容：旧的 __PLAN__: 前缀消息（已废弃）
        if (m.role === 'assistant' && typeof m.content === 'string' && m.content.startsWith('__PLAN__:')) {
          // ... 保留原有解析逻辑不变 ...
        }
      }

      if (!page || page === 1) {
        messages.value = list
      } else {
        messages.value = [...list, ...messages.value]
      }
    } catch {
      // silent
    }
  }
```

#### 关键变化

| 项目 | 修改前 | 修改后 |
|------|--------|--------|
| 检测方式 | `content.startsWith('__PLAN__:')` | `m.message_type === 'plan_result'` |
| 数据源 | 从 content 中解析 JSON（格式脆弱） | 从 `m.metadata.summary` 读取（结构稳定） |
| Markdown | 必须客户端生成 | 优先用后端已存的 Markdown，没有才生成 |
| 向后兼容 | 无 | `__PLAN__:` 分支作为降级保留 |

#### 已知的降级场景

- 用户打开一个更新前创建的旧会话，其中的消息仍然以 `__PLAN__:` 前缀存储
- 如果 `m.message_type` 是 `'text'` 但 `content` 以 `__PLAN__:` 开头，进入降级分支
- 降级分支会在 `__PLAN__:` 消息被新方案消息替代后自然淘汰

### 2. `sendMessage()` 中 Done 事件处理简化

**文件**: `frontend/src/store/chatStore.ts`（`handleSSEEvent` 函数）

#### 当前行为

`done` 事件处理（约第 523 行）：
1. 检查 `status === 'waiting_input'` 则跳过
2. 调用 `generatePlanMarkdown(summary)` 生成 Markdown
3. push 一条 `message_type: 'plan_result'` 的消息到消息列表
4. 调用 `normalizeSSESummary(summary)` 更新 `planStore.currentPlan`

#### 修改内容

后端修改后，方案 Markdown 和 summary 会通过 `record_plan_result()` 持久化到 DB。但 SSE 流中前端仍然需要即时渲染，所以 SSE 处理逻辑基本不变，只需确保推入消息列表的消息格式与后端一致：

```typescript
// done 事件处理（主要改动在第 2 点）
if (evt === 'done') {
  const doneData = data as SSEDoneData
  if (doneData.status === 'waiting_input') break

  const s = doneData.summary
  if (s && s.daily_itinerary) {
    // 生成 Markdown 用于即时显示
    const md = generatePlanMarkdown(s)
    // push 到消息列表（与后端持久化的格式一致）
    chatMessages.value.push({
      id: `plan_${Date.now()}`,
      session_id: sessionId.value,
      role: 'assistant',
      content: md,
      message_type: 'plan_result',
      metadata: {
        plan_id: doneData.plan_id,
        summary: s,
      },
      created_at: new Date().toISOString(),
    } as any)
  }
  // 更新实时方案面板（SSE 传来的 summary 格式）
  pStore.currentPlan = {
    ...pStore.normalizeSSESummary(s || {}),
    id: doneData.plan_id || '',
    content_blocks: doneData.content_blocks || [],
  } as any
  pStore.isGenerating = false
}
```

### 3. 无需修改的内容

以下前端逻辑不需要修改，因为后端实现 `save_pipeline_output()` 并完善 `_to_response()` 后，这些功能会自然修复：

| 功能 | 无需修改的理由 |
|------|---------------|
| `planStore.fetchPlanDetail()` | 后端 `GET /plans/{id}` 返回完整的 `PlanResponse`（含详细字段）后，无需前端额外映射 |
| `planStore.normalizeSSESummary()` | SSE 事件触发的即时渲染仍然需要它进行实时格式转换 |
| `generatePlanMarkdown()` | 即时生成本地显示的 Markdown 仍然需要 |
| 方案面板渲染组件 | 后端返回完整数据后，面板自然显示完整内容 |

## 验证方法

1. **新方案验证**: 发送旅行需求 → 管线完成 → 刷新页面 → 打开同一会话 → 确认方案 Markdown 正确显示，实时方案面板恢复
