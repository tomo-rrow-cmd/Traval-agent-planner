> **状态：✅ 已应用（2026-07-10）** — 本文档为修复方案的历史记录，所列问题已全部修复并合入主分支。保留本文档供参考修复思路和设计决策。

> 实施修订（2026-07-10）：本文最初方案中的 Alembic 模型导入问题经核对并不存在；
> `env.py` 已完整导入 `Conversation`、`Message` 和 `ConversationPlanRun`。实际实现采用下述
> 原子持久化方案：`conversation_plan_runs.summary` 是结构化方案唯一来源，`messages.content`
> 保存 Markdown，`messages.metadata_json` 仅保存 `plan_run_id`。历史 API 查询时批量关联 run，
> 动态向响应的 `metadata.summary` 注入结构化方案，避免数据库重复保存大型 JSON。

> 同时纳入修复：消息真实 ID/时间戳透传、页码与双向游标分页、会话所有权校验、

> 原文中先 `create_plan_run()`、再单独 `record_plan_result()` 的两事务示例不再采用。

## 一、遇到的问题

### 问题 1：方案管线输出未完整持久化

检查 `chat.py` 中 `_run_pipeline_events()` 的 done 事件处理器时发现，它已经调用了 `service.create_plan_run()`，该方法会将管线输出写入 `conversation_plan_runs.summary` JSON 列。但 **方案结果的 Markdown 内容没有被持久化**——done 处理器只存储了原始 JSON 数据，没有把面向用户展示的 Markdown 文本存入 `messages` 表。

**后果**：用户刷新页面后，前端无法直接恢复方案 Markdown 展示，只能依赖已废弃的 `__PLAN__:` 前缀 hack 来解析 JSON 重新生成。

### 问题 2：消息类型无法区分

`messages` 表只有 `role`、`content`、`sequence` 三列，没有任何字段标记"这条消息是方案结果"。前端收到消息时需要通过 `content.startsWith('__PLAN__:')` 这种字符串前缀来判断——不稳定且已标记废弃。

**后果**：`loadHistory()` 需要做脆弱的字符串解析，后端也无法精确知道哪些消息是方案结果。

### 问题 3：消息元数据无法存储

`messages` 表没有 `metadata` 列，`plan_result` 消息无法关联到对应的 `conversation_plan_runs` 记录 ID。方案结果消息和它的原始数据之间没有关联关系。

**后果**：前端收到 `plan_result` 消息后，无法通过消息本身追溯到后端的方案运行记录。

### 问题 4：Alembic 迁移模型导入不全

`app/db/migrations/env.py` 中没有导入 `Conversation`、`Message`、`ConversationPlanRun` 模型（实际代码中 `ConversationPlanRun` 已导入，但 `Conversation` 和 `Message` 需要确认），导致 `alembic autogenerate` 无法检测到这些表的变更。

## 二、现有代码分析（为什么要这么改）

### 已做过什么

在分析过程中发现，**后端代码实际上已经做了大部分持久化工作**，只是不是我们最初认为的方式：

| 组件 | 实际状态 | 发现过程 |
|------|---------|---------|
| `conversation_plan_runs` 表 | ✅ 已定义并有 `summary` JSON 列 | 读取 `app/db/models/conversation.py` 发现该模型存在 |
| `create_plan_run()` 方法 | ✅ 已实现（Repository + Service 两层） | 读取仓库和服务层代码确认调用链完整 |
| `chat.py` done 处理器 | ✅ 已调用 `service.create_plan_run()` | 读取 `chat.py` 第 162-175 行发现 |
| `__PLAN__:` 机制 | ⚠️ 已废弃，但无替代方案 | 读取 `chatStore.ts` `loadHistory()` 发现 |

### 为什么简化方案可行

**核心洞察**：管线输出的完整 JSON（含 `destination`、`days`、`daily_itinerary`、`budget`、`traffic` 等）已经通过 `create_plan_run()` → `repo.create_plan_run()` 写入了 `conversation_plan_runs.summary` 列。这不是"部分数据"，而是**完整管线输出**。

所以我们不需要：
- `Plan` 模型加 `raw_plan_data` 列 → **不需要**，`conversation_plan_runs.summary` 已存储
- 实现 `save_pipeline_output()` → **不需要**，`create_plan_run()` 已实现相同功能
- 重写 `_to_response()` → **不需要**，`plans` 表不是方案数据的主要存储位置
- 修改 Exporter → **不需要**，导出时可以从 `conversation_plan_runs` 读取

原方案最初归纳为：
1. `messages` 表加 `message_type` 和 `metadata_json` 列 → 让方案结果消息可识别、可关联
2. done 处理器持久化 Markdown 文本到 `messages` 表
3. 各层透传新字段 → 让前端能看到这些新字段

## 三、修改方式（具体步骤）

### 步骤 1：Message 模型加两列

**文件**: `app/db/models/conversation.py`

**原因**：当前 `Message` 模型没有区分消息类型的字段，也没有元数据字段。`message_type` 用来标注"这是方案结果"（`plan_result`），`metadata_json` 用来存储关联的 `plan_run_id` 和 `summary` 引用。

**修改**：在 `sequence` 列后新增两列：

```python
# 当前 import 行需要加 JSON
from sqlalchemy import Column, String, Text, Integer, DateTime, ForeignKey, JSON

class Message(Base, UUIDMixin, TimestampMixin):
    __tablename__ = "messages"

    conversation_id = Column(String(36), ForeignKey("conversations.id"), nullable=False)
    role = Column(String(20), nullable=False, doc="user / assistant / system")
    content = Column(Text, nullable=False)
    sequence = Column(Integer, default=0, doc="消息序号（递增）")
    # 新增以下两列
    message_type = Column(String(30), default="text", doc="text / plan_result / plan_progress")
    metadata_json = Column(JSON, default=dict, doc="方案结果时存 {plan_run_id, summary}")
```

**数据流变化**：
```
修改前：messages 表只有 role + content + sequence
修改后：messages 表有 role + content + sequence + message_type + metadata_json
  → plan_result 消息示例：message_type="plan_result", 
    metadata_json={"plan_run_id": "run_xxx", "summary": {"destination": "大理", ...}}
  → 前端通过 message_type === 'plan_result' 即可识别
```

### 步骤 2：ConversationRepository 扩展

**文件**: `app/db/repositories/conversation_repo.py`

#### 2a: `add_message()` 支持新字段

**原因**：调用方需要能传入 `message_type` 和 `metadata_json`，Repository 必须将它们写入数据库。

**修改**：在 `add_message()` 方法签名中增加可选参数，构造 `Message` 时传入：

```python
async def add_message(self, conv_id: str, role: str, content: str,
                      message_type: str = "text",
                      metadata_json: dict | None = None) -> Message:
    result = await self.db.execute(
        select(func.coalesce(func.max(Message.sequence), 0))
        .where(Message.conversation_id == conv_id)
    )
    seq = result.scalar_one() + 1
    msg = Message(
        conversation_id=conv_id, role=role, content=content, sequence=seq,
        message_type=message_type,
        metadata_json=metadata_json or {},
    )
    self.db.add(msg)
    await self.db.flush()
    return msg
```

**设计考虑**：
- `message_type` 默认 `"text"`，现有调用方不需要修改
- `metadata_json` 默认 `None`，传 `None` 时存空 dict——确保兼容性

#### 2b: `get_messages()` 返回新字段

**原因**：Repository 只返回 `role` 和 `content`，上层 Service 无法拿到 `message_type` 和 `metadata`。前端通过 API 获取消息时得不到这些字段，`loadHistory()` 就无法按 `message_type` 检测。

**修改**：返回值中增加 `message_type` 和 `metadata`：

```python
async def get_messages(self, conv_id: str, limit: int = 50) -> list[dict]:
    result = await self.db.execute(
        select(Message)
        .where(Message.conversation_id == conv_id)
        .order_by(Message.sequence.asc())
        .limit(limit)
    )
    return [{
        "role": m.role,
        "content": m.content,
        "message_type": m.message_type,
        "metadata": m.metadata_json or {},
    } for m in result.scalars().all()]
```

**注意**：返回的字段名用 `"metadata"` 而非 `"metadata_json"`（数据库列名），因为前端的 `MessageRecord` schema 用 `metadata`。

### 步骤 3：ConversationService 扩展

**文件**: `app/services/application/conversation_service.py`

#### 3a: `record_ai_reply()` 支持可选参数

**原因**：后续如果需要将 AI 回复标记为 `plan_progress` 等类型，需要能传入 `message_type` 和 `metadata`。

**修改**：

```python
async def record_ai_reply(self, session_id: str, content: str,
                           message_type: str = "text",
                           metadata: dict | None = None):
    async with async_session_factory() as db:
        repo = ConversationRepository(db)
        await repo.add_message(session_id, "assistant", content,
                               message_type=message_type,
                               metadata_json=metadata)
        await db.commit()
```

**设计考虑**：默认值保持向后兼容，现有调用方不需要改。

#### 3b: 新增 `record_plan_result()` 方法

**原因**：需要一个专门的方法来持久化方案结果消息，它做的事情和普通 AI 回复不同——需要同时存 Markdown（给用户看）和 summary（给前端面板恢复用）。

**修改**：

```python
async def record_plan_result(self, session_id: str, summary: dict,
                              plan_run_id: str, markdown: str):
    """持久化方案结果消息（替代 __PLAN__: 机制）"""
    async with async_session_factory() as db:
        repo = ConversationRepository(db)
        await repo.add_message(
            conv_id=session_id,
            role="assistant",
            content=markdown,
            message_type="plan_result",
    metadata_json={"plan_run_id": plan_run_id},
        )
        await db.commit()
```

**数据存储示例**：

```
messages 表：
  role: "assistant"
  content: "# 🗺️ 大理3日之旅\n\n**北京 → 大理** · **3天**\n\n## 📅 第1天\n### 大理古城..."
  message_type: "plan_result"
  metadata_json: {"plan_run_id": "run_20260710_abc"}
```

前端拿到后：
- `message_type === 'plan_result'` → 这是方案结果
- `content` → 直接显示 Markdown（不需要再生成）
- 历史 API 根据 `plan_run_id` 从 `conversation_plan_runs.summary` 动态注入 `metadata.summary`
  → 前端传给 `normalizeSSESummary()` 恢复方案面板

**原因**：当前第 137-141 行硬编码了 `message_type="text"` 和 `metadata={}`，导致 repository 返回的正确值被覆盖，前端永远看不到新字段。

### 步骤 4：Chat API Done 处理器增加 Markdown 持久化

**文件**: `app/api/v1/chat.py`

**原因**：当前 done 处理器只调用了 `create_plan_run()` 存储 JSON 数据，没有生成和存储 Markdown 文本。前端 SSE 过程中会调用 `generatePlanMarkdown()` 在客户端生成 Markdown，但这个 Markdown 只存在于内存中，刷新后丢失。

**修改**：在 `create_plan_run()` 成功后，调用 `record_plan_result()`：

```python
async for evt, data in run_pipeline(pipeline_params):
    if evt == "done":
        summary = data.get("summary") or {}
        if service and hasattr(service, "create_plan_run"):
            try:
                plan_run = await service.create_plan_run(session_id, summary)
                data["plan_id"] = plan_run.id

                # 新增：持久化方案 Markdown 消息
                # 方案内容已在 conversation_plan_runs.summary 中持久化，
                # 但面向用户展示的 Markdown 文本需要存到 messages 表，
                # 这样前端 loadHistory() 时直接读取 Markdown 内容，
                # 无需重新生成或解析 __PLAN__: 前缀
                if summary:
                    from app.services.export.exporter import export_markdown
                    markdown = export_markdown(summary)
                    await service.record_plan_result(
                        session_id=session_id,
                        summary=summary,
                        plan_run_id=plan_run.id,
                        markdown=markdown,
                    )
            except Exception:
                data["plan_id"] = f"plan_{session_id[:8]}"
        else:
            data["plan_id"] = f"plan_{session_id[:8]}"
        data["session_id"] = session_id
    yield (evt, data)
```

**完整数据流**：

```
管线 done 事件
  ↓
create_plan_run(session_id, summary)
  ├─→ conversation_plan_runs 表写入 ←── 已有（管线输出JSON）
  └─→ conversations.plan_id = run.id  ←── 已有（会话关联）
  ↓
export_markdown(summary)            ←── 新增：生成 Markdown
  ↓
record_plan_result(...)             ←── 新增：持久化方案消息
  ├─→ messages 表写入：
  │   message_type = "plan_result"
  │   content = "# 🗺️ 大理3日之旅..."
  │   metadata_json = {"plan_run_id": "run_xxx", "summary": {...}}
  └─→ 前端 loadHistory() 时恢复
```

**为什么用 `export_markdown()`**：
- 该函数已在 `exporter.py` 中存在，专用于从管线输出格式的 dict 生成 Markdown
- 和前端 `generatePlanMarkdown()` 功能重叠，但后端生成的优势是：一次生成、永久存储、全端一致
- 当 summary 数据不完整时，`export_markdown()` 会输出部分内容但不会报错——安全

## 六、最终实施与验收记录（2026-07-10）

本文前述内容保留为问题分析和方案演进记录；最终实现以本节及当前代码为准。

### 6.1 已落实的闭环修复

- 方案 run、会话完成状态和 `plan_result` Markdown 消息在同一事务中持久化；任一步骤失败均不 commit，SSE 只发送 `error`，不再伪造 ID 或继续发送 `done`。
- `done.plan_run_id` 明确指向 `conversation_plan_runs.id`；`plan_id` 暂作为同值兼容别名，不代表 `plans.id`。
- 历史消息透传真实 `id`、`created_at`、`message_type`；run summary 通过批量查询动态注入响应的 `metadata.summary`，数据库 `messages.metadata_json` 不重复保存 summary。
- 消息 API 支持页码、`before_id` 和 `after_id` 分页；分页参数互斥，无效或跨会话游标返回 400，双向结果均按时间正序返回。
- GET `/stream` 统一身份与会话所有权校验，只恢复已持久化的最终状态；`lastEventId` 保留兼容但不承诺事件级续传。
- 客户端发送使用稳定 `client_message_id`，重试复用同一 ID；同一会话内由唯一约束防止重复消息。
- 消息和 run 分配 sequence 前锁定 Conversation 行；会话内 sequence 由数据库唯一约束保证不重复。
- 会话列表批量返回真实消息数、最后消息预览和最新 `plan_run_id`，并保持活动时间与置顶排序语义。
- 会话状态更新不再隐式改名；默认会话由首条用户消息命名，显式创建标题和用户手工重命名均保持不变。
- 前端历史恢复不再把 run ID 请求到 `/plans/{id}`；兼容新格式、旧 `__PLAN__:` 数据、无 summary 和损坏旧数据。
- 前端收到 SSE `error` 时结束方案生成状态并清理进度，避免保存失败后持续显示生成中。
